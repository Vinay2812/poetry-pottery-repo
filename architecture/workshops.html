Workshops

Open studio booking is the only part of the system where capacity cannot be expressed as a counter. A session occupies one or more grid hours, several bookings share an hour, and the number of free wheels is a sum over the live bookings' slot rows. So the guard is a per-studio transaction-scoped advisory lock, taken before any occupancy is read, with a pure schedule module deciding what the grid looks like and which picks are legal.

Architecture

How it works

The schedule grid

api/src/features/workshops/schedule.ts is pure and timezone first, and it is borrowed whole by studio visits, which run buildAvailability and checkSlots over a half-hour grid with a capacity of one. All conversion goes through Intl.DateTimeFormat, cached per zone, with hourCycle: "h23". toWallClock(instant, tz) gives { date, weekday, minutes } and fromWallClock(date, minutes, tz) returns a UTC instant using two correction passes so daylight saving offsets converge. addDays is pure string arithmetic over date keys.

Availability

buildAvailability({ config, from, days, now, blackouts, occupants }) decides each day in this precedence: a past day is closed with reason Past; a day beyond the booking window is closed with Bookings open N days ahead; a closed weekday is Studio closed. Otherwise it emits slots, and each slot is judged in this order: before the lead time is Too soon; an overlapping blackout uses the blackout's own reason or Studio closed; zero remaining is Fully booked; otherwise it is available. remaining is reported even on unavailable slots. A day whose slots are all unavailable is closed with No sessions left.

Overlap is half open (a.starts_at < b.ends_at && a.ends_at > b.starts_at), so adjacent hours do not collide. occupancy(slot, occupants) sums participants over the occupants overlapping that slot.

Multi-hour bookings

  • slotsPerBooking(hours, config) is Math.max(1, Math.round(hours * 60 / slot_minutes)), so a two hour tier on a sixty minute grid needs two picked hours. They need not be contiguous.
  • spanDays(starts, tz) counts studio-local calendar days from the earliest to the latest pick, inclusive, and checkSlots refuses a span beyond slot_span_days with Keep every hour on the same day or Keep every hour within N days of the first.
  • slotBounds(starts, slotMinutes) produces the booking's starts_at and ends_at as a bounding box, not a contiguous block. The authoritative hours are the WorkshopBookingSlot rows.

checkSlots runs, in order: the participant range against capacity_per_slot; the exact hour count; duplicate instants via a Set of timestamps; then per slot the lead time, the booking window, the closed weekdays, grid alignment (no stray seconds or milliseconds, and (start.minutes - opening_minutes) % slot_minutes === 0, else Choose an hour from the calendar), the studio hours, and any blackout overlap; then the span rule; and finally capacity per chosen hour independently, so a two hour booking whose first hour is full fails as a whole.

The advisory lock

Capacity has no counter column: it is derived by summing participants over the slot rows of live bookings. That cannot be guarded by a conditional update, so it is guarded by a lock. WorkshopsService.lock(configId) runs SELECT pg_advisory_xact_lock(${configId}), the single-argument form, where the key is the WorkshopConfig.id itself with no hashing or namespacing. It is transaction scoped, so it releases on commit or rollback, and it cannot collide with the cart's two-integer lock because Postgres keeps the two key spaces apart. It serialises every booking, reschedule and reopen write for one studio; different studios proceed in parallel.

Correctness depends entirely on every writer taking the lock before reading occupancy. All three writers do: book, reschedule, and applyStatus when re-entering a seat-holding state.

Booking

  1. configBySlug with is_active: true, including tiers ordered by hours; a miss is a 404.
  2. lock(config.id) - first, before any occupancy read.
  3. Tier lookup by exact hours; a miss lists the available durations.
  4. Build the request with the slot starts sorted ascending and the participants truncated.
  5. assertSlots fetches the overlapping blackouts and the active bookings in parallel, then calls checkSlots; any failure is a bad request carrying the reason the container toasts.
  6. slotBounds, then pricing: subtotal = tier.price_per_person * participants, discount: 0, total = subtotal, pieces_per_person copied from the tier. The client never sends a price.
  7. Create the booking with newPublicId("WS") and one WorkshopBookingSlot row per hour.
  8. After commit, the guest and studio mails.

Availability queries

availability validates that from matches YYYY-MM-DD, clamps days to 1 to MAX_AVAILABILITY_DAYS = 31, and pads the query range by a day on each side in UTC so timezone offsets cannot clip an edge slot. It fetches blackouts and activeBookings in parallel and then runs the pure buildAvailability. It takes no lock and no transaction: the numbers it returns are advisory, and the booking transaction is the authority.

activeBookings reads workshopBookingSlot rows overlapping the range whose booking belongs to this config and holds seats, optionally excluding one booking. Because occupancy is derived from live rows rather than stored, there is no counter to drift, and cancelling frees hours implicitly by status.

Reschedule and cancel

reschedule finds the booking scoped by user, checks can_reschedule (can_cancel || (status === CONFIRMED && starts_at > now), so confirmed guests may move but not self cancel), takes the lock, and builds the request from the current hours and participants because the client may only choose new times. assertSlots is called with the booking's own id excluded, so moving onto an hour it already partly occupies is legal. It then deletes every slot row and creates the new set inside the same locked transaction, so the intermediate zero-slot window is invisible to other bookers.

cancel checks can_cancel and calls applyStatus with "USER" as the cancelled_by. No slot rows are deleted; the hours free up because activeBookings filters on the seat-holding statuses.

WorkshopsService.applyStatus reuses the events transition table. Moving from a non-holding into a holding state re-takes the lock and re-validates the hours before re-holding. The transition itself is the same status-predicated compare and swap, whose zero count raises ConflictException("This booking was just updated, refresh and try again"). cancelled_by is USER | ADMIN | SYSTEM.

Admin configuration

  • assertHours validates the merged current-plus-input values, so a partial patch cannot create an invalid studio day: opening at or after zero, closing at or below 1440, closing after opening, and slot_minutes between 15 and the length of the day.
  • assertWeekdays requires integers 0 to 6; assertPositive covers capacity, booking window and span.
  • Tiers upsert on @@unique([config_id, hours]), so saving the same length edits rather than duplicates.
  • Blackouts are arbitrary instants rather than slot aligned, and match by overlap, so a partial-hour blackout kills the whole hour.

The client

  • useAvailability(configSlug, monthKey, isSkipped) fetches one whole calendar month per request and keeps the previous grid visible while the next month loads. The reschedule dialog skips the query until it opens.
  • WorkshopBookingContainer derives dayByKey and slotByStart indexes, computes needed = slotsNeeded(hours, slot_minutes) mirroring the server, and enforces the span rule in the UI as well through isDayWithinSpan.
  • togglePicked ignores extra picks once the needed count is reached; changing the duration clears every pick; raising the participant count prunes picks the bigger group has outgrown. A picked but now disabled slot stays clickable so a guest can always un-pick.
  • BookingDetailContainer holds useOptimistic(booking, applyBookingAction) with cancel and reschedule actions, the latter recomputing the bounding box from the sorted set the same way slotBounds does. Opening the move dialog seeds the picker with the existing slots so most hours can be kept.

Hours picked ahead

When the page loads, and again after the length changes, suggestSlots in features/workshops/types.ts fills the session for the visitor from the loaded month: it takes the free days from today inside the studio's slot_span_days window and fills them in layers, one hour on every day first, then a second hour on the earliest days, and so on, so hours spread as thin as the window allows and only stack when they must. Within a day it takes the earliest hours, so stacked hours run back to back. It tries each start day in turn and returns the first window that holds the whole session, or null, which the summary reports as toUnavailableMessage. The container derives the picks from that suggestion until the first hand-made change (hasTouched), after which the visitor's own list is the truth; picking a new length starts the suggestion over.

Edge cases and failure handling

  • Two parties for the last wheel are serialised by the advisory lock; the loser re-reads the committed occupancy and is refused.
  • A multi-hour booking where only some hours have room fails as a whole, because every hour is checked inside the same locked transaction and any failure rolls back the create. The integration spec asserts that no half-written booking reserved the free hour.
  • The same hour picked twice is caught by the Set check and backed by @@unique([booking_id, starts_at]).
  • Daylight saving is handled by the two-pass fromWallClock, covered by a Europe/London case in the schedule spec.
  • Availability the browser holds is always stale by design. The booking mutation re-validates and its message is what the container toasts.
  • There is no database backstop for capacity. No unique constraint spans bookings and there is no exclusion constraint, so a future writer that forgets lock(config_id) could overbook with nothing to catch it. Event seats, by contrast, are guarded by the conditional update itself, and studio visits by a partial unique index that no writer can forget.
  • Shrinking capacity or narrowing hours does not re-validate existing bookings; they survive and only new ones are blocked.
  • Mails are enqueued after commit and their failure is not swallowed, so a mail error rejects a mutation whose booking already exists.

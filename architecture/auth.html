Auth and user provisioning

Clerk owns sessions on both sides; the API owns identity. Every request passes through Clerk's Express middleware, a request id, a globally registered throttler guard, and then either no guard at all (public), an optional-auth call into the guard, AuthGuard, or AdminGuard. The guard resolves a User row from the Clerk auth id, provisioning it just in time on first sight and repairing claims that have drifted, and the role on that row - never the claim - is what the admin gate compares.

Architecture

How it works

Boot order

api/src/main.ts:bootstrap applies helmet (with CSP and COEP relaxed outside production so Apollo Sandbox loads), sets trust proxy to env.TRUSTED_PROXY_HOPS, enables CORS for env.CORS_ORIGINS with credentials, then installs clerkAuthMiddleware(). That wrapper around @clerk/express's clerkMiddleware() skips Clerk entirely for GET /graphql outside production, because Clerk's dev handshake redirects document requests away from the Sandbox. AppModule.configure then applies RequestIdMiddleware to every route, and registers GqlThrottlerGuard as APP_GUARD and AllExceptionsFilter as APP_FILTER.

There is no hand-rolled JWT code anywhere. The token is verified by Clerk's middleware using CLERK_PUBLISHABLE_KEY and CLERK_SECRET_KEY; guards read the result through getAuth(request). clerk.util.ts:readAuthId wraps getAuth in a try-catch, because getAuth throws when the middleware never ran, and that case is treated as anonymous rather than as an error.

The authenticate algorithm

api/src/common/guards/auth.guard.ts:AuthGuard.authenticate runs these steps in order.

  1. Return req.authenticatedUser if it is already set. GraphQL can invoke a guard once per field, so this memo makes it one authentication per request.
  2. getAuth(request); when auth.isAuthenticated is false, throw UnauthorizedException("Authentication required").
  3. Read dbUserId and role out of auth.sessionClaims as a hint only.
  4. UsersService.findByAuth(authId), a findUnique on auth_id. The row that owns the auth id decides identity.
  5. Stale claim repair. If a row exists and either dbUserId or role disagrees with it, call ClerkService.updatePublicMetadata(authId, { dbUserId: owner.id, role: owner.role }). The returned AuthUser is always built from the row, never from the claim.
  6. JIT provisioning. With no row, ClerkService.getUser(authId), then getPrimaryEmail (the address matching primaryEmailAddressId, else emailAddresses[0]). No email is UnauthorizedException("No primary email found"). getFullName falls back to first plus last name and then to null; getImageUrl likewise.
  7. Inside PrismaService.withTransaction, UsersService.upsertUser on auth_id and then updatePublicMetadata. The upsert never writes role: create defers to the schema default USER and update omits the column, so a new user cannot be minted as an admin.
  8. Assign req.authenticatedUser and return it.

Profile drift is only repaired in one direction. A user whose row already exists never has email, name or image refreshed from Clerk; the update branch of the upsert is in practice reachable only when a concurrent request created the row between the lookup and the write.

Admin gate

api/src/common/decorators/auth.decorators.ts is four lines: AuthRequired() applies UseGuards(AuthGuard) and AdminRequired() applies UseGuards(AdminGuard). AdminGuard extends AuthGuard rather than running beside it, calls the inherited authenticate, and throws ForbiddenException("Administrator access required") unless user.role === UserRole.ADMIN. Because the role compared is the database column, a forged or stale role: ADMIN claim cannot pass.

There is no @Public() or @OptionalAuth() decorator. Public means the absence of a guard, so access control here is opt-in rather than deny by default. Optional auth is done by injecting AuthGuard as a plain provider and calling authGuard.tryAuthenticate(context.req), which swallows only UnauthorizedException and returns null. That pattern now carries four write paths, not just field resolvers: subscribing to the newsletter, watching a sold-out piece, filing a commission brief and booking a studio visit are all open to anyone and file the row against an account when there happens to be one. Two of those resolver specs assert the absence of guard metadata, so being public is a tested invariant rather than an oversight.

Throttling

GqlThrottlerGuard extends Nest's ThrottlerGuard and is registered globally, so it runs before any route guard. It overrides getRequestResponse with the GraphQL-aware helper in common/graphql/execution-context.ts, returns true for contexts that are neither http nor graphql (queue consumers pass through global guards too), and swallows any error that is not a ThrottlerException so a Redis outage cannot take the API down.

Frontend side

  • frontend/src/app/layout.tsx wraps the tree in ClerkProvider and then ApolloProvider.
  • frontend/src/proxy.ts is Next 16's renamed middleware and is a bare clerkMiddleware(). It establishes the session and protects no route.
  • frontend/src/lib/apollo/links.ts:createAuthLink sets the bearer header from useAuth().getToken; the RSC client in rsc-client.ts does the same with auth().getToken() and also forwards x-forwarded-for, so server side calls are not all throttled as the Next server's own address.
  • frontend/src/features/auth/hooks.ts:useRequireAuth opens the sign-in prompt through useUIStore instead of firing an unauthenticated mutation. SignInWall is the page level equivalent.
  • ClearStoreOnUserChange in apollo-provider.tsx calls client.clearStore() whenever the Clerk userId changes after the first settle, which covers sign-out and account switching in one place.

Edge cases and failure handling

  • Two concurrent first requests from one new user. Both see no row and both upsert on the unique auth_id. There is no P2002 catch in the guard or in UsersService, so the loser surfaces as a generic 500 through AllExceptionsFilter. The client's retry succeeds because the row now exists: self healing, but a real error window.
  • Email collisions do not self heal. User.email is unique. A Clerk account deleted and recreated with the same email, or an email changed to one another row already holds, hits users_email_key with no handler, which is a persistent 500 for that user on every authenticated request until it is fixed by hand.
  • Clerk is called inside the provisioning transaction. updatePublicMetadata is a network call inside withTransaction, so provisioning is atomic (there is never a row without metadata) at the cost of holding the transaction open and depending on Clerk being reachable for a first sign-in. The claim repair path writes nothing to the database and is deliberately not transactional.
  • Role revoked mid-session. The old token still says admin, but AdminGuard re-reads the row on every request, so API access stops immediately; the console catches up on the next useUser() settle.
  • Clerk profile with no email is refused with UnauthorizedException("No primary email found") and no row is created.
  • A resolver that forgets its guard but uses @CurrentUser throws InternalServerErrorException("CurrentUser requires an auth guard on the resolver"), a 500 that is logged and sent to Sentry rather than an anonymous fallback.
  • Throttler storage outage fails open by design: the guard allows the request.
  • Production introspection without x-schema-key is refused with a GraphQL FORBIDDEN error.
  • Because access is opt-in, a new resolver with no decorator is public. The admin tree puts @AdminRequired() on each method rather than on the class, so a forgotten decorator there would be silently public. api/src/features/admin/admin-guards.spec.ts now walks every field of all fourteen admin resolver classes and asserts the guard, which closes that hole for the admin tree; the four guarded fields on storefront resolvers are outside its sweep and rely on their own resolver specs.

Tests

  • api/src/common/guards/auth.guard.spec.ts is the main coverage: seven AuthGuard cases (rejects the unauthenticated, accepts matching claims with no Clerk calls, ignores a stale dbUserId, ignores an ADMIN claim the database does not back, provisions on incomplete claims and asserts the upsert shape including the absent role, rejects a missing email, caches per request) plus two AdminGuard cases.
  • api/src/features/users/users.service.spec.ts covers the findByAuth where clause and the upsertUser passthrough.
  • api/test/helpers/execution-context.ts:createHttpExecutionContext builds a real Nest execution context so guards can run without a server.
  • api/src/common/graphql/logging.plugin.spec.ts asserts the log line carries req.authenticatedUser.db_user_id; api/src/common/graphql/introspection.plugin.spec.ts covers the schema key gate.
  • api/src/features/admin/admin-guards.spec.ts is parameterised over the fourteen admin resolvers and asserts AdminGuard on every field of each; commissions.resolver.spec.ts and visits.resolver.spec.ts assert guard metadata in both directions, including that the public fields carry none.
  • Not covered by a spec: clerk.service.ts, clerk.util.ts, current-user.decorator.ts, and every frontend auth module apart from SignInPromptDialog.stories.tsx. gql-throttler.guard.spec.ts does now exist.

Branch stack and PRs

The rewrite ships as a stack of branches, one per feature, each cut from the previous one and each intended to become its own pull request. It is linear as far as feat/workshops; after that the design refresh and the reviews branch are siblings from the same commit, and the admin work continues from reviews. This page records the shape as it actually is on the remote, with the commit counts that were measured rather than assumed.

Architecture

How the stack is built

The rewrite is built as one pull request per feature, each branch stacked on the previous one. The owner opens the pull requests from the pushed branches, so a branch described as pushed is ready for a review rather than already merged.

Where the line actually forks

The stack is strictly linear from main through feat/workshops. After that it is not. feat/design-refresh is a one-commit sibling of feat/reviews, not its ancestor:

  • origin/feat/reviews..origin/feat/design-refresh is 1 commit, a0da4a8, an editor configuration change.
  • origin/feat/design-refresh..origin/feat/reviews is 6 commits.
  • The merge base is therefore at depth 90 from origin/main, at ea20279 docs: describe the storefront, data flow and verification after the refresh, which is design-refresh~1. feat/reviews was cut from there.
  • The arithmetic checks out: origin/feat/design-refresh..origin/feat/admin is 20, which is 110 minus 90.
  • origin/feat/admin..origin/feat/reviews and origin/feat/reviews..origin/feat/workshops are both empty, confirming that workshops, reviews, admin and admin-ui are strict ancestors of each other in that order.

The README's branches table records feat/reviews as "Rebased on feat/design-refresh locally, not yet pushed". That is now stale: origin/feat/reviews exists, and it sits on design-refresh~1 rather than on design-refresh.

What the 78 commit design refresh body contains

Between feat/workshops and the fork point sit the storefront redesign, the content, newsletter and contact API, the legacy import trio, the archive and made-to-order work, the per-hour workshop slot model, the motion and optimistic UI pass, and the concurrency hardening that the integration specs on the testing page cover - notably 59e2441 test: prove stock, seat, slot and coupon guards under concurrency, 46ec1c1 fix: quote an order from the same reading of the shelf that takes the stock and c94eebb fix: keep two tabs from losing each other's cart additions.

Local branches

  • docs/architecture is this documentation branch, cut from feat/admin-ui.
  • feat/custom-piece-photos sits 16 commits past origin/feat/admin-ui and test/coverage-gaps 13 past it; neither is pushed.
  • Four review branches - fix/admin-review, fix/admin-ui-review, fix/reviews-review and fix/ui-review - hold cross-review fixes.
  • Local main is one unpushed commit ahead of origin/main.
  • Several worktree-agent-* branches are pinned at origin/main and are scaffolding for isolated agent worktrees.

Commit conventions

  • Conventional commits, enforced by commitlint in the commit-msg hook.
  • A single subject line per commit, with no body and no attribution trailers.
  • pre-commit runs lint-staged so every commit is already formatted.
  • pre-push runs the schema sync check, so a branch cannot be pushed with a stale api/schema.gql or stale generated frontend hooks.

Minimal theory: how to reproduce these numbers

  1. git fetch originRefresh the remote refs before measuring anything.
  2. git log --oneline origin/main..origin/<branch> | wc -lThe commit count for each row of the table above.
  3. git log --oneline origin/feat/reviews..origin/feat/design-refresh | wc -lReturns 1, which is what shows the two are siblings rather than ancestor and descendant.
  4. git merge-base origin/feat/design-refresh origin/feat/reviewsResolves to ea20279, at depth 90 from origin/main.
  5. git log --oneline origin/feat/admin..origin/feat/reviews | wc -lReturns 0, confirming reviews is a strict ancestor of admin.
  6. scripts/check-schema-sync.shWhat the pre-push hook runs before any of these branches can be published.

Things to watch when working on the stack

  • Rebasing a lower branch rewrites every branch above it. The stack is ten deep, so a change to feat/catalog propagates through eight rebases.
  • feat/design-refresh is not in the ancestry of feat/admin-ui. Its one distinguishing commit, the editor configuration change, is not present on the admin branches; everything else that branch is credited with landed before the fork point and is shared.
  • The README's branch table is the human-facing summary and has drifted on the reviews row.
  • Local branches ahead of origin/feat/admin-ui mean the tip of the stack on the remote is not the newest work in the repository.
  • The schema sync hook can fail a push for a reason that is not in your diff, if api/schema.gql was committed stale earlier in the stack. It regenerates in place, so the fix is to commit what it wrote.

Gates that run per branch

  • commitlint on every commit message, conventional commits.
  • lint-staged Prettier on every commit.
  • scripts/check-schema-sync.sh on every push: schema freshness, generated hook freshness, and a frontend typecheck against the schema.
  • Per branch, before a pull request: pnpm build, pnpm test, pnpm lint and pnpm schema:emit in api/, and pnpm tsc, pnpm test, pnpm lint, pnpm knip and pnpm codegen in frontend/.

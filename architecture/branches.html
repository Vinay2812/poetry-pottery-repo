Branch stack and PRs

The rewrite ships as ten stacked branches, one per feature, each cut from the previous one and each open as its own pull request, numbered one to ten in that order. That is how the pull requests are wired on GitHub. The commit graph underneath is very slightly different: the line is strictly linear as far as feat/workshops, and after that feat/design-refresh and feat/reviews are siblings from a common commit rather than parent and child. This page records both, with numbers that were measured rather than assumed.

Architecture

How the stack is built

One pull request per feature, each branch stacked on the previous one, all ten open and none merged. The owner opens them from the pushed branches, so a branch here is ready for a review rather than already in main.

Where the line actually forks

The graph is strictly linear from main through feat/workshops. After that it is not, and the pull request bases smooth over a fork that is really there.

  • git merge-base origin/feat/design-refresh origin/feat/reviews resolves to 208b065 fix: keep the products query the 404 shelf reads from, at depth 185 from origin/main and 173 commits past feat/workshops.
  • Both branches sit exactly 15 commits past that point, which is why both read 200. Neither contains the other: origin/feat/reviews..origin/feat/design-refresh and its mirror are both 15.
  • feat/admin descends from feat/reviews, so design-refresh's last fifteen commits are not in the admin branches. That is not cosmetic. The archive and unsubscribe routes moving onto PageShell, the archive tab becoming a real link, the flaw shot stopping being the first gallery photo, and the whole brand - a drawn Wordmark, eleven files under frontend/public/brand and a validated NEXT_PUBLIC_SITE_URL - all live on that side of the fork only. Several pages here say so where it matters.
  • Pull request 8 still names feat/design-refresh as its base, so GitHub shows reviews' own fifteen commits and the fork does not surface in the review. It will surface at merge time.

Local branches

The remote is not the newest work. At the time these pages were verified:

  • feat/admin is 9 commits ahead of origin/feat/admin.
  • feat/admin-ui is 44 ahead of and 26 behind origin/feat/admin-ui: the remote has been rebased since the local branch was cut, so the two have diverged rather than simply drifted.
  • docs/architecture is these pages, cut from the local feat/admin-ui tip 14a020d test: assert the piece update input carries the new fields, and it inherits that divergence. Everything on these pages was read out of that working tree.
  • main is one unpushed commit ahead of origin/main.
  • feat/category-pieces and fix/admin-verify are scratch branches, and several worktree-agent-* branches are scaffolding for isolated agent worktrees.

A branch called feat/logo held the brand work while these pages were being written and was folded into feat/design-refresh before they were finished; it no longer exists. That is the ordinary shape of this stack, and it is why every number on this page is a snapshot with the command that produced it rather than a fact to be trusted later.

Commit conventions

  • Conventional commits, enforced by commitlint in the commit-msg hook.
  • A single subject line per commit, with no body and no attribution trailers.
  • pre-commit runs lint-staged so every commit is already formatted.
  • pre-push runs the schema sync check, so a branch cannot be pushed with a stale api/schema.gql or stale generated frontend hooks.

Minimal theory: how to reproduce these numbers

  1. git fetch originRefresh the remote refs before measuring anything; this stack is rebased often.
  2. gh pr list --state all --json number,headRefName,baseRefNameThe ten pull requests and the base each one names.
  3. git rev-list --count origin/main..origin/<branch>The commit count for each row of the table above.
  4. git merge-base origin/feat/design-refresh origin/feat/reviewsResolves to 208b065, which is the fork point rather than either branch's tip.
  5. git rev-list --count 208b065..origin/feat/design-refreshReturns 15, and the same command against origin/feat/reviews returns 15 as well, which is what shows they are siblings.
  6. git rev-list --count origin/feat/reviews..origin/feat/adminReturns 25, confirming reviews is a strict ancestor of admin.
  7. git for-each-ref --format='%(refname:short) %(upstream:track)' refs/heads/Where each local branch stands against its remote, including the ahead-and-behind pairs.
  8. scripts/check-schema-sync.shWhat the pre-push hook runs before any of these branches can be published.

Things to watch when working on the stack

  • Rebasing a lower branch rewrites every branch above it. The stack is ten deep, so a change to feat/catalog propagates through eight rebases and invalidates every number on this page.
  • feat/design-refresh is not in the ancestry of feat/admin-ui. Fifteen commits of storefront fixes and the entire brand are on the other side of the fork, so a fix made there has to be cherry-picked or waited for.
  • The pull request base hides the fork. PR 8 reviews cleanly against design-refresh; the divergence only appears when the two are actually merged.
  • The remote tip is not the newest work. Local feat/admin and feat/admin-ui both run ahead, and feat/admin-ui has also been rebased on the remote, so the two have genuinely diverged.
  • These pages are verified against a working tree, not a remote. Anything read here reflects the local feat/admin-ui tip.
  • The schema sync hook can fail a push for a reason that is not in your diff, if api/schema.gql was committed stale earlier in the stack. It regenerates in place, so the fix is to commit what it wrote.
  • A new resolver must be exported from api/src/resolvers.ts or schema:emit drops it silently and the frontend never sees the field, which is the failure the hook will report as a codegen diff rather than as a missing resolver.

Gates that run per branch

  • commitlint on every commit message, conventional commits.
  • lint-staged Prettier on every commit.
  • scripts/check-schema-sync.sh on every push: schema freshness, generated hook freshness, and a frontend typecheck against the schema.
  • Per branch, before a pull request: pnpm build, pnpm test, pnpm lint and pnpm schema:emit in api/, and pnpm tsc, pnpm test, pnpm lint, pnpm knip and pnpm codegen in frontend/.
  • For anything that touches a race, pnpm -C api test:integration three times, because the verification skill counts one failure in three as a finding rather than a flake.

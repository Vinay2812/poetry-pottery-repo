Branch stack and PRs

The rewrite ships as ten stacked branches, one per feature, each cut from the previous one and each open as its own pull request, numbered one to ten in that order. The commit graph underneath now agrees with that in full: it is one strictly linear line from origin/main to feat/admin-ui, with the documentation branch on the end. It has not always been — feat/design-refresh and feat/reviews were siblings from a common commit for a while, and that fork is the reason several of these pages once carried a "not in this branch's ancestry" caveat. The restack removed it. This page records the shape and the numbers, measured rather than assumed.

Architecture

How the stack is built

One pull request per feature, each branch stacked on the previous one, all ten open and none merged. The owner opens them from the pushed branches, so a branch here is ready for a review rather than already in main.

The fork, and the restack that closed it

The graph used to stop being linear after feat/workshops. git merge-base of design-refresh and reviews resolved to 208b065 fix: keep the products query the 404 shelf reads from, and both branches sat fifteen commits past it as siblings, so design-refresh's last fifteen commits were not in the admin branches even though pull request 8 named design-refresh as its base. That was not cosmetic: the archive and unsubscribe routes moving onto PageShell, the words-only seconds block, the pending-upload sweep, the glaze table behind the commission form and the whole brand lived on one side of the fork only.

The stack has since been replayed so that every pull request base is also the real parent:

  1. feat/reviews onto feat/design-refresh with a plain git rebase, because the old base was still an ancestor of both.
  2. feat/admin onto the new feat/reviews with git rebase --onto, because the reviews commits had been rewritten and their patch ids no longer matched.
  3. feat/admin-ui onto the new feat/admin, replayed on a scratch branch and then moved with git update-ref, because the branch is checked out in another worktree and cannot be checked out twice.
  4. docs/architecture onto the finished feat/admin-ui, again with --onto from the commit it was originally cut at.

Three kinds of conflict came out of it, all of them the two sides having done the same work differently: the storage service (design-refresh had renamed keyFromUrl to keyFor and added PendingUploadsService, while reviews and admin still called the old name), the integration harness (both sides had added providers to the same array), and the generated artefacts. api/schema.gql and frontend/src/graphql/generated/graphql.tsx were never merged by hand: pnpm schema:emit and pnpm codegen regenerated them at each stop. One reviews commit disappeared entirely, because design-refresh had already made the same change to the queue topology test.

Local branches

The remote is not the newest work, and after a restack the local branches are not simply ahead of it. Measured at the time this page was last verified:

  • feat/design-refresh, feat/reviews and feat/admin have been force-pushed since the restack and are level with their remotes, nothing ahead and nothing behind.
  • feat/admin-ui is 93 ahead of and 92 behind its remote, and docs/architecture 110 ahead and 108 behind. The behind counts are the pre-restack commits the remote still holds, not work that is missing locally; both branches are waiting to be pushed.
  • docs/architecture is these pages, cut from the local feat/admin-ui tip and rebased onto it again after the restack. Everything here was read out of that working tree.
  • main is one unpushed commit ahead of origin/main.
  • The backup/* refs that held the pre-restack tips have been deleted; a worktree-agent-* branch remains as scaffolding for an isolated agent worktree, and it is not part of the stack.

A branch called feat/logo held the brand work while these pages were first being written and was folded into feat/design-refresh; a one-commit chore/gitignore-env-prod was folded in the same way during the restack. Both are gone. That is the ordinary shape of this stack, and it is why every number on this page is a snapshot with the command that produced it rather than a fact to be trusted later.

Commit conventions

  • Conventional commits, enforced by commitlint in the commit-msg hook.
  • A single subject line per commit, with no body and no attribution trailers.
  • pre-commit runs lint-staged so every commit is already formatted.
  • pre-push runs the schema sync check, so a branch cannot be pushed with a stale api/schema.gql or stale generated frontend hooks.

Minimal theory: how to reproduce these numbers

  1. git fetch originRefresh the remote refs before measuring anything; this stack is rebased often.
  2. gh pr list --state all --json number,headRefName,baseRefNameThe ten pull requests and the base each one names.
  3. git rev-list --count origin/main..origin/<branch>The commit count for each row of the table above.
  4. git merge-base feat/design-refresh feat/reviewsNow resolves to the feat/design-refresh tip itself, which is what shows the fork is closed. Against the origin/ refs it still resolves to 208b065.
  5. git rev-list --count feat/design-refresh..feat/reviewsReturns 14, the reviews commits alone; the mirror returns 0, because design-refresh is now a strict ancestor.
  6. git rev-list --count feat/reviews..feat/adminReturns 38, and feat/admin..feat/admin-ui returns 40; both confirm a strict ancestor rather than a sibling.
  7. git for-each-ref --format='%(refname:short) %(upstream:track)' refs/heads/Where each local branch stands against its remote, including the ahead-and-behind pairs.
  8. scripts/check-schema-sync.shWhat the pre-push hook runs before any of these branches can be published.

Things to watch when working on the stack

  • Rebasing a lower branch rewrites every branch above it. The stack is ten deep, so a change to feat/catalog propagates through eight rebases and invalidates every number on this page.
  • A restack is the only way to move a fix down the stack. When design-refresh was a sibling rather than an ancestor, a storefront fix made there could not be seen from the admin branches at all; replaying the stack was what fixed that, and cherry-picking would only have duplicated the commits.
  • Regenerate, never hand-merge, the generated files. api/schema.gql and frontend/src/graphql/generated/graphql.tsx conflict on almost every restack and a hand-resolved version is wrong the moment a resolver moves. pnpm schema:emit then SCHEMA_URL=../api/schema.gql pnpm codegen is the resolution.
  • The remote tip is not the newest work. Every branch above design-refresh reads as both ahead of and behind its remote, because the restack rewrote commits the remote still holds. Publishing the stack means force-pushing it from the bottom up, in order.
  • These pages are verified against a working tree, not a remote. Anything read here reflects the local feat/admin-ui tip.
  • The schema sync hook can fail a push for a reason that is not in your diff, if api/schema.gql was committed stale earlier in the stack. It regenerates in place, so the fix is to commit what it wrote.
  • A new resolver must be exported from api/src/resolvers.ts or schema:emit drops it silently and the frontend never sees the field, which is the failure the hook will report as a codegen diff rather than as a missing resolver.
  • A branch checked out in another worktree cannot be rebased in this one. Replay it on a scratch branch and move the real ref with git update-ref refs/heads/<branch> <new> <old>, which fails rather than clobbers if the branch moved underneath you.

Gates that run per branch

  • commitlint on every commit message, conventional commits.
  • lint-staged Prettier on every commit.
  • scripts/check-schema-sync.sh on every push: schema freshness, generated hook freshness, and a frontend typecheck against the schema.
  • Per branch, before a pull request: pnpm build, pnpm test, pnpm lint and pnpm schema:emit in api/, and pnpm tsc, pnpm test, pnpm lint, pnpm knip and pnpm codegen in frontend/.
  • For anything that touches a race, pnpm -C api test:integration three times, because the verification skill counts one failure in three as a finding rather than a flake.

Frontend data layer

The frontend has one rule that shapes everything else: Apollo is for fetching, and nothing hand-edits its cache. Optimism is React 19's useOptimistic and useTransition in a container, over a pure reducer that lives in the feature's types.ts and is unit tested there; the new baseline is either the mutation payload or an awaited refetch; and a failure rolls back by itself and shows a toast. URL-driven state - filters, sorting, tabs, pagination - uses the same pattern and keeps previous results on screen rather than flashing skeletons.

Architecture

How it works

Two clients, one link factory

frontend/src/lib/apollo/links.ts exports createHttpLink() (pointing at clientEnv.NEXT_PUBLIC_API_URL with credentials: "include") and createAuthLink(getToken: TokenGetter), which awaits the getter and sets the bearer header only when a token exists. That TokenGetter type is the only seam between browser Clerk and server Clerk.

  • Browser. apollo-provider.tsx:ApolloProvider holds getToken from useAuth() in a ref that an effect keeps fresh, and builds the client through useCallback(..., []). The empty dependency array is deliberate: a token rotation must ride the ref, never rebuild the client, or the cache would be dropped on every refresh. makeClient composes the auth link and the http link over an InMemoryCache, using @apollo/client-integration-nextjs rather than @apollo/client directly.
  • Server. rsc-client.ts uses auth().getToken(), adds forwardVisitorIp to copy the incoming x-forwarded-for or x-real-ip onto the outbound request, and exports getClient, query and PreloadQuery from registerApolloClient, which gives one client per request so repeated server calls dedupe. Only getClient is actually used, by lib/data/site-settings.ts and the eleven readers in lib/data/catalog.ts.

frontend/src/lib/apollo/index.ts exports exactly one symbol, ApolloProvider; the RSC client is imported by full path so server-only code never reaches the client barrel.

There is no error link

No ErrorLink or onError exists anywhere. Errors surface in three places instead: containers read error off the generated hook and render a component such as LoadFailed; mutation handlers catch and raise toast.error(toErrorMessage(error)); and server reads in catalog.ts inspect CombinedGraphQLErrors and call notFound() only for a genuine 404, rethrowing anything else so it becomes an error page. One consequence is that an expired token surfaces per call as a toast, with no global handler.

Fetch only, never hand-edit the cache

The rule in the root CLAUDE.md, elaborated in docs/design/optimistic-audit.md, has four beats: the baseline is data ?? previousData; the optimistic layer is a pure reducer living in the feature's types.ts and unit tested there; useTransition drives aria-busy and dimmed opacity rather than a skeleton once content has shown; and the settle comes from the mutation payload or from refetchQueries with awaitRefetchQueries, with a sonner toast as the only rollback signal.

Resetting the store on an account change

ResetStoreOnUserChange renders null and sits inside the provider. It bails while Clerk has not settled, treats the first settle as "not a change" using an undefined sentinel in the ref, and otherwise calls client.resetStore(), toasting on failure. That covers sign-out and account switching in one place, and it replaced a hand maintained list of user-scoped root fields to evict. The source comment records the choice over clearStore: resetting restarts the queries it cancels instead of leaving them empty, which matters because the header's badge queries are live at that moment.

docs/design/optimistic-audit.md still names client.clearStore() in three places. The repo rule in CLAUDE.md and the code both say resetStore; clearStore appears nowhere in frontend/src.

URL-driven state

Three implementations share one shape: the URL is the source of truth, useOptimistic covers only the navigation latency, and the navigation is router.replace(..., { scroll: false }).

  • ProductListContainer is the reference implementation, with a reducer, a pendingRef so rapid clicks stack, a 300 ms search debounce, a local search draft so the field never snaps back mid-navigation, and useDeferredValue so the input paints per keystroke while results follow.
  • EventListContainer uses the reducer-free form, passing whole filter objects.
  • useAdminQueryState in the admin shell is the shared console version; see the admin page.

Keeping previous results visible

The idiom is data?.x ?? previousData?.x, which needs notifyOnNetworkStatusChange: true. Skeletons render only when loading && !result. Everything else is isBusy driving aria-busy and a dimmed opacity. Appending is excluded from isBusy so the load-more control owns that state. Infinite scroll uses a callback ref that creates an IntersectionObserver with rootMargin: "600px 0px", reading the handler through a ref so the observer is never rebuilt.

Codegen

frontend/codegen.ts loads .env.local then .env itself. SCHEMA_URL defaults to the running API; when it starts with http codegen introspects with an x-schema-key header carrying SCHEMA_SYNC_KEY, and otherwise it is treated as a file path, which is how the pre-push hook regenerates offline against ../api/schema.gql. Output is one file, src/graphql/generated/graphql.tsx, with DateTime mapped to string, type imports on, and descriptions disabled so URL and file introspection produce byte-identical output. A post-codegen script, scripts/strip-suspense-hooks.ts, removes the suspense hooks that ship a @ts-ignore and do not typecheck on Apollo v4, and exits 1 if it matched nothing, so a codegen upgrade fails loudly rather than shipping ignores.

Environment and stores

  • frontend/src/config/env.ts parses clientEnv eagerly from static process.env.NEXT_PUBLIC_* references so Next can inline them, and exposes getServerEnv(), which throws if called in the browser and memoises its result.
  • frontend/src/store/ui-store.ts is the whole of Zustand in this app: one slice holding isSignInPromptOpen with its open and close actions, consumed only by useRequireAuth and SignInPromptContainer. Zustand is for interface state; server data never goes in it. Shared optimistic state gets a feature context provider instead, which is what CartProvider and WishlistProvider are.
  • frontend/src/components/providers/toaster.tsx is a single sonner Toaster at bottom right, offset 24 pixels in from both edges and 80 pixels up on mobile to clear the bottom nav, with containerAriaLabel="Studio notices" naming its live region. The shell that mounts it is described on the shell page.
  • next.config.ts turns on the React Compiler, lists the remote image patterns, marks winston as a server external package and aliases it to a browser stub in Turbopack.

Edge cases and failure handling

  • No global error handling. A 401 after a token expires is a per-call thrown error and a toast.
  • The client must never be rebuilt on a token refresh, which is why makeClient is memoised with an empty dependency array and the getter lives in a ref.
  • ResetStoreOnUserChange needs its undefined sentinel; without it the store would be reset on every first paint, because Clerk reports a null user id before hydration.
  • Suspense is required wherever a container calls useSearchParams, which is why /products, /search, /events, the admin workshops, reviews and inbox routes, and the header's own mobile menu container all wrap their children and the others do not.
  • query and PreloadQuery are exported from rsc-client.ts but never imported; any streaming work would start there.
  • The optimistic audit is stale on the number of sanctioned updateQuery calls and on the name of the lifecycle call.
  • A GraphQL error with cached previousData keeps stale content on screen rather than showing the failure state, which only renders when there is no result at all.

Tests

  • Every optimistic reducer and pure derivation is unit tested in its feature's types.test.ts: 35 such files, 17 on the storefront and 18 under features/admin.
  • frontend/src/store/ui-store.test.ts covers the one Zustand slice; frontend/src/lib/format.test.ts covers the formatters.
  • frontend/vitest.config.ts defines two projects: unit in jsdom, and storybook, which runs all 253 .stories.tsx files in a real headless Chromium with a11y: { test: "error" }, so an accessibility violation fails the run.
  • Containers and providers themselves have no tests; the reducers they call do.
  • pnpm knip guards dead exports, with production entries declared in frontend/knip.ts.

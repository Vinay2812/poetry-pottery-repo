Admin API and console

The admin console is a second Next.js route group talking to a second GraphQL surface. Fourteen NestJS modules under api/src/features/admin expose most of the studio's write operations, every field behind @AdminRequired(), and the console under frontend/src/app/(admin)/dashboard renders one container per screen on top of a shared shell, a shared UI kit and one hook that keeps list state in the URL. The rule that keeps the two halves honest is that admin services do not re-implement domain logic: order, registration, booking, visit and review transitions all route back through the same services the storefront uses. Two admin surfaces, order notes and the commission inbox, are guarded fields on storefront resolvers rather than modules of their own.

Architecture

How it works

One guard, not a chain

api/src/common/decorators/auth.decorators.ts is four lines of composition: AuthRequired() applies UseGuards(AuthGuard) and AdminRequired() applies UseGuards(AdminGuard). AdminGuard extends AuthGuard and calls its protected authenticate helper, then rejects anything whose database role is not UserRole.ADMIN. The role is read from the User row, not from the Clerk claim, so a stale claim cannot grant access. Every field in every admin module carries @AdminRequired(); there is no unguarded field in the admin tree.

setUserRole is the only admin field that also injects @CurrentUser() actor, because self-demotion is checked against actor.db_user_id.

Shared admin helpers

  • api/src/features/admin/admin.type.ts holds AdminUserRef, AdminPageInput, toUserRef(), searchTerm() (trim, then null when empty) and trimmed(value, max). Console search is a plain contains match, not the storefront semantic index.
  • api/src/features/admin/slug.ts holds slugify() (NFKD, lowercase, non-alphanumerics to dashes, 80 characters) and uniqueSlug(base, taken), which appends -2, -3 and so on.

Two admin surfaces that are not admin modules

Both break the features/admin/<name> convention deliberately, and both put @AdminRequired() on the individual field instead.

  • Order notes. addOrderNote is a guarded mutation on the storefront OrdersResolver, because the note is a customer-facing thing written onto an order and it reuses orderInclude and toOrder wholesale. It is the only caller of assertConfirmed outside the admin tree. See the checkout page.
  • The commission inbox. commissionRequests, markCommissionRequestRead and setCommissionRequestStatus sit on CommissionsResolver beside the three public fields. See the commissions page.

The consequence is that api/src/features/admin/admin-guards.spec.ts, which walks every field of fourteen resolver classes and asserts AdminGuard on each, does not see either of them. They are covered by their own resolver specs instead.

The packing slip

There is no packing slip API field. /dashboard/orders/[id]/packing-slip reuses useAdminOrderQuery and renders PackingSlip; printing is window.print(). What makes it a real document is an @media print block in globals.css with @page { margin: 14mm }, which hides header[data-admin-chrome], both nav[aria-label="Studio sections"] variants and the sonner toaster, and zeroes the main padding. The on-screen Print and Back buttons carry print:hidden. hide_prices drops the money columns and the totals list; the gift note and the care lines print regardless.

Console shell

The gate is applied twice by different mechanisms. frontend/src/app/(admin)/dashboard/layout.tsx runs on the server, reads Clerk's currentUser() and redirects to / when publicMetadata.role is not UserRole.Admin; it also sets robots: { index: false, follow: false }. AdminChromeContainer repeats the check in the browser with useUser() and calls router.replace("/") when the role changes under a session that is already open.

frontend/src/features/admin/shell/types.ts holds ADMIN_NAV_LINKS (fifteen sections now) and isNavLinkActive, where /dashboard matches exactly and every other link owns its subtree. The rail reads Dashboard, Pieces, Categories, Glazes, Orders, People, Events, Workshops, Visits, Commissions, Reviews, Content, Coupons, Inbox and Waiting list, which is the restock notifications screen under a name a potter would use.

URL state and the optimistic pattern

frontend/src/features/admin/shell/hooks.ts:useAdminQueryState is the backbone of every list screen. The URL is the source of truth and the optimistic layer covers only the navigation: useOptimistic(urlValues, applyQueryPatch) plus useTransition, with a pendingRef so rapid filter clicks stack instead of clobbering each other. applyQueryPatch deletes page on any patch that is not an explicit page move, drops empty strings from the URL, and toQueryString sorts keys so the URL is stable. useSearchDraft debounces at SEARCH_DEBOUNCE_MS = 300 and clears its local draft when the committed value changes underneath it.

Twenty-four files under features/admin use useOptimistic, all with the same shape: derive rows, useOptimistic(rows, applyXPatch), then inside startTransition patch first, await the mutation, refetch(), toast on failure and clear the busy id in finally. ReviewsContainer is the clearest example; ContactMessagesContainer uses applyContactPatch with { kind: "read" } and { kind: "remove" }; CatalogContainer is the only container with two row lists under useOptimistic at once. Nothing rolls back by hand: React discards the optimistic value when the transition ends and the refetch() reconciles.

Lists use fetchPolicy: "cache-and-network" with data ?? previousData, so changing a filter never blanks the table. Only the first load shows a skeleton, marked aria-busy="true".

Uploader

The console never sends bytes through the API. ImageUploaderContainer reads the rules from the imageSpecs query, checks the file, measures it with createImageBitmap, centre-crops when the ratio is wrong, PUTs the blob straight to the presigned R2 URL and then asks the API to confirm it. A file below the minimum pixel size is fatal before the crop dialog opens, because cropping cannot add pixels. The full presign and confirm algorithm is on the storage and uploads page.

Client validation

frontend/src/lib/validations/admin/ holds eight zod modules (catalog, content, coupon, event, glaze, order, product, workshop), each with a test sibling. They compare datetime-local and HH:mm values as strings, since both formats are fixed width and sort like the instants they encode. Client zod is defence in depth only: every rule has a server counterpart in assertMoney, assertStock, assertMeasurements, assertSecond, parseColorCode, parseCoupon, assertDispatchDays, assertHours, assertWeekdays and assertWindow.

Dashboard numbers

AdminDashboardService.summary(now = new Date()) takes an injectable clock so the spec can pin the window, and runs ten queries in one Promise.all: an order groupBy by status, a 30 day order aggregate that yields both the count and the revenue, pending booking and registration counts, the unread message count, new commission briefs (status: NEW), upcoming visits (starts_at >= now and cancelled_at: null, so cancelled and past windows are excluded), a low stock list, and the five most recent orders and bookings.

  • PAID_STATUSES = [PAID, SHIPPED, DELIVERED], so orders_last_30_days means paid orders in 30 days, not orders placed.
  • The window filters on created_at, so an old order paid today does not appear.
  • LOW_STOCK_THRESHOLD = 2 with lte, excluding is_customizable pieces because they are made to order, capped at 12 rows with no pagination.
  • The two newest tiles are the ones that answer "is anyone waiting on me": briefs nobody has looked at, and live windows still ahead of now.
  • fillStatusCounts fills every OrderStatus member with zero so the tile row never reflows.
  • item_count is summed in JavaScript from line quantities, not line count. There is no caching layer: every dashboard load runs all eight queries.

Minimal theory: call trace

An admin mutation, for example hiding a review

  1. frontend/src/features/admin/reviews/containers/ReviewsContainer.tsx:handleToggleHiddenClick handler. Opens startTransition, calls patchRows({ kind: "hidden", id, isHidden }) first so the row flips immediately.
  2. frontend/src/graphql/admin/reviews.gqlThe SetReviewHidden operation that codegen turned into useSetReviewHiddenMutation.
  3. frontend/src/lib/apollo/links.tsAuth link attaches the Clerk session token to the outgoing GraphQL request.
  4. api/src/common/guards/admin.guard.ts:AdminGuard.canActivateResolves the request via getRequest(context), calls the inherited authenticate, then rejects any role other than UserRole.ADMIN with ForbiddenException.
  5. api/src/common/guards/auth.guard.ts:AuthGuard.authenticateMemoised per request. Reads Clerk auth, looks the user up by auth id, repairs a drifted claim, and JIT-provisions on first sight.
  6. api/src/features/admin/reviews/reviews.resolver.ts:AdminReviewsResolver.setReviewHiddenThe guarded mutation field.
  7. api/src/features/admin/reviews/reviews.service.ts:AdminReviewsService.setHiddenInside prisma.withTransaction: reads the row, takes reviews.lockSubject(subjectOf(current)) so moderation pins the same row a customer post would, updates is_hidden, then recomputes through reviews.refreshRating.
  8. frontend/src/features/admin/reviews/containers/ReviewsContainer.tsx:refetchAwaited after the mutation resolves; the refetched list becomes the new baseline and the optimistic value is discarded.

Edge cases and failure handling

  • An empty batch cannot go live. assertCanBeLive in products.service.ts runs on create and on setActive(id, true), the only two ways a piece is put on the shelf: without stock the piece stays archived unless it is made to order. A live piece that sells out is not touched, so it stays editable and the shelf rule alone hides it. The console mirrors this with canGoLive: the Restore button, the list checkbox and the create form's "Live on the shelf" box are disabled with the reason shown.
  • The last admin cannot step down. UsersService.setRole counts the other admins before any demotion and refuses when there are none, on top of the existing rule that you cannot demote yourself. The person page asks for the admin total and disables the button with the same sentence, so the refusal is never a surprise.
  • Two gates, two sources of truth. The server layout reads the Clerk claim, AdminGuard reads the database row. A stale claim can reach the console shell, but every GraphQL field still returns 403.
  • Self-demotion is blocked. users.service.ts:setRole refuses when id === actingUserId and the new role is not admin.
  • Duplicate coupon codes. Prisma P2002 is caught by rethrowDuplicate and re-thrown as ConflictException("That code already exists") on create and update.
  • Admin transitions never bypass the shared state machine. An admin cancel routes through the same applyStatus as a customer cancel, so stock release and coupon restoration happen once, in one place.
  • Cancelling an event is a loop of awaits, one applyStatus plus notifyStatus per live registration. It is not batched and not transactional across registrations, so a failure part way through leaves some guests cancelled and the event still published.
  • assertConfirmed is a no-op when R2 is not configured, so local development without storage is not blocked and the confirmation gate is inactive there.
  • Both exports are queries that perform an export, returning a whole CSV as one GraphQL string, capped at EXPORT_LIMIT with no streaming, no pagination and a silent cap. The browser turns the string into a file itself, with a Blob, a synthetic <a download> and a revoked object URL.
  • The guard sweep does not reach every admin field. admin-guards.spec.ts walks the fourteen resolver classes under features/admin, so addOrderNote and the three commission fields are outside its sweep and rely on their own resolver specs.
  • Deleting a glaze pieces wear is refused, even though the foreign key is SetNull and would have allowed it silently.
  • ImageListUploaderContainer silently drops a duplicate URL instead of saying so.
  • Only the inbox, reviews and workshops routes wrap their container in Suspense, although useAdminQueryState calls useSearchParams() on every list screen.

Tests

  • API: one service spec per module, api/src/features/admin/{catalog,content,coupons,dashboard,events,glazes,inbox,orders,products,reviews,uploads,users,visits,workshops}/<name>.service.spec.ts.
  • api/src/features/admin/admin-guards.spec.ts is parameterised over all fourteen admin resolver classes and asserts that every field of each one carries AdminGuard. There is still no admin.guard.spec.ts of its own; the role check is covered by two cases inside auth.guard.spec.ts.
  • api/test/integration/admin.integration-spec.ts adds seven console-versus-shopper races against a real Postgres: seats held while an event edit is in flight, two concurrent room resizes, shrinking a room past held seats, the last three pieces going to the console or the buyer but never both, a console stock count never undoing a sale, refusing to call off an evening that has already run, and only one of two concurrent status moves landing.
  • Frontend: eighteen types.test.ts files under features/admin cover the optimistic reducers and row mappers, across catalog, commissions, content, coupons, dashboard, events, glazes, inbox, notifications, orders, people, pieces, reviews, shell, ui, uploads, visits and workshops.
  • Validation: frontend/src/lib/validations/admin/{catalog,content,coupon,event,glaze,order,product,workshop}.test.ts.
  • Every admin component has a .stories.tsx sibling; Storybook is the component test surface. There are no container tests, and hooks.ts in shell and uploads is untested.

Studio visits

A studio visit is half an hour of someone's time, not a wheel and not a seat. There is no counter and no lock: the calendar is advisory, the booking writes first and asks questions afterwards, and the one thing standing between two people reaching for the same window is a partial unique index on starts_at WHERE cancelled_at IS NULL. That predicate is the whole design. It is also the one constraint in the schema that Prisma cannot express, so it exists only in migration SQL.

Architecture

How it works

The model, and the constraint that is not in it

StudioVisit is small: id as nanoid(12), starts_at, ends_at, name, phone, an optional note, a nullable cancelled_at, a nullable user_id with onDelete: SetNull, and created_at. There is no status enum: booked means cancelled_at IS NULL, and the console derives its label from that. The GraphQL type deliberately omits user_id and created_at.

schema.prisma declares only two plain indexes, on starts_at and user_id, because Prisma has no syntax for a partial unique index. The real constraint is written by hand, and the migration says why:

api/prisma/migrations/20260917140000_studio_visit_cancellation/migration.sql, in full.
StatementWhy
ALTER TABLE "studio_visits" ADD COLUMN "cancelled_at" TIMESTAMP(3);Cancellation becomes a stamp rather than a delete.
DROP INDEX "studio_visits_starts_at_key";The original total unique, created by 20260917120000_studio_visits, held a cancelled window closed forever.
CREATE UNIQUE INDEX "studio_visits_live_starts_at_key" ON "studio_visits"("starts_at") WHERE "cancelled_at" IS NULL;Keeps the race on the live rows only, so a cancelled window goes back on offer.

This is the only database constraint in the system that the Prisma schema does not describe. A prisma db push, or a migrate diff taken from the schema rather than the migration history, would drop it and silently take the guard off the whole feature.

The grid, borrowed whole

VisitsService.config() does not have a configuration table of its own. It reads the first active WorkshopConfig and borrows its timezone and opening hours, falling back to FALLBACK_HOURS (Asia/Kolkata, 720 to 1140 minutes, so noon to seven) when there is none. It then overrides the rest with visit values: slot_minutes: VISIT_SLOT_MINUTES = 30, capacity_per_slot: 1, booking_window_days: 14, slot_span_days: 1.

With that shape in hand, availability and validation are the pure workshop schedule module: buildAvailability for the calendar and checkSlots for the booking, both from api/src/features/workshops/schedule.ts. A capacity of one turns the workshop occupancy sum into a simple taken-or-free test, which is why the same code serves both. availability(from, days) clamps the span to MAX_DAYS = 21, fetches blackouts and occupants in parallel, and renames slots to windows on the way out. Occupants are studioVisit.findMany rows overlapping the range with cancelled_at: null, which is what puts a cancelled window straight back on the calendar.

Booking is a write, not a check

bookStudioVisit carries no guard and @StrictThrottle(). Like the commission brief, it injects AuthGuard as a plain provider and calls tryAuthenticate, passing user?.db_user_id ?? null, so anyone can come by and a signed-in visitor gets the row filed against their account. The resolver spec asserts the absence of guard metadata, so being public is a tested invariant rather than an oversight.

  1. parseVisitInput: name 2 to 80, phone through the shared normalisePhone, note trimmed to 500 with blank becoming null.
  2. endsAt = startsAt + 30 minutes.
  3. checkSlots validates the hours, the half-hour grid alignment, the two-hour lead time and any blackout overlap.
  4. It never asks whether the window is free. The source says so outright: whether the window is free is left to the unique start, so a taken window always comes back with the same sentence.
  5. studioVisit.create inside a try. The catch narrows on Prisma.PrismaClientKnownRequestError with error.code === "P2002" and throws BadRequestException("Someone just took that window, pick another"); anything else is rethrown.

Because there is no read before the write, there is no window in which two callers can both see a free slot. Postgres serialises the two inserts on the index and one of them raises. This is the cheapest correct guard in the codebase: no advisory lock like workshops, no conditional update like event seats, no row lock like checkout.

Cancelling

The mutation cancelStudioVisit(id, reason) is admin only, on AdminVisitsResolver, but the behaviour lives in the storefront VisitsService.cancel, which the admin service calls in one line. The admin module owns the authorisation, the storefront module owns the mail.

  • findUnique including user.email; a miss is NotFoundException("Visit not found").
  • Idempotent: an already-cancelled visit returns early, writes nothing and mails nothing.
  • Otherwise it stamps cancelled_at. The row is never deleted, so the window's history survives while the partial index stops counting it.
  • The reason is trimmed and cut to 300 characters, or null.

The visitor is never mailed on booking. An anonymous visit captures a name and a phone number but no email address, so there is nothing to write to; the confirmation is on screen, through toConfirmationLine. The studio copy compensates with a prebuilt https://wa.me/91<phone>?text=... link labelled "Send them a WhatsApp confirmation".

studioVisitCancelledMail sets its call to action to { label: "Pick another window", path: "/visit" }, and there is no /visit route. The booking UI lives on /contact. That link is a dead end in a mail a visitor actually receives.

The storefront UI

There is no dedicated route: app/(storefront)/contact/page.tsx renders StudioVisitContainer beside the contact form. The feature is VisitDayStrip, VisitWindowPicker and VisitForm over pure helpers in frontend/src/features/visits/types.ts (VISIT_DAYS = 14, toDateKey, toWindowLabel, firstOpenDate, windowsFor, countOpen, toConfirmationLine), with the form schema in frontend/src/lib/validations/visit.ts. Everything renders in a hard-coded Asia/Kolkata.

The container's catch block is the client half of the race protocol, and it is two lines: clear the picked window, then await refetch(). A lost race means the calendar on screen is stale, so the refetched grid becomes the new baseline rather than the client trying to reason about what changed.

The day sheet

AdminVisitsService.list(filter) orders by starts_at: "asc" rather than the usual created_at: "desc", because the studio reads it as a day sheet. MAX_LIMIT = 60. Cancelled rows are hidden unless include_cancelled is set; from and to build a starts_at range; search matches the name case-insensitively or the phone exactly. Each row carries the visit, the customer reference when the booking was signed in, and created_at.

The console converts its date filters to IST-anchored ISO with a hard-coded IST_OFFSET = "+05:30", making the to day inclusive to its last millisecond. Cancelling goes through the shared AdminReasonDialog with the reason optional, an optimistic applyVisitPatch, an awaited refetch, and the toast "Visit cancelled and the window is free again".

Edge cases and failure handling

  • Two people reaching at once: one insert wins, the other gets P2002 and the same sentence a stale calendar would have produced. There is no lock to forget to take.
  • A cancelled window is bookable again immediately, because the unique index ignores rows with a cancelled_at, and the cancelled row stays for the record.
  • Cancelling twice is a no-op and sends no second mail.
  • The partial index is invisible to Prisma. Nothing in schema.prisma would recreate it; only the migration history carries it.
  • Availability is advisory. It takes no lock and no transaction, and the booking is the authority; the container answers a refusal with a refetch rather than a guess.
  • An anonymous booking gets no email, on booking or on cancellation, because no address was collected.
  • The cancellation mail links to /visit, which does not exist.
  • Visit hours follow the wheel sessions. Changing the workshop config's opening hours silently moves the visit grid, and there is no separate setting to stop that.
  • Existing visits are not revalidated when the hours narrow or a blackout is added; only new bookings are refused.

Tests

  • api/src/features/visits/visits.service.spec.ts covers the input parsing, the borrowed configuration and its fallback hours, the grid and lead-time refusals, and the idempotent cancel.
  • api/src/features/visits/visits.resolver.spec.ts asserts that neither field carries guard metadata, so the public booking path cannot be closed by accident.
  • api/src/features/admin/visits/visits.service.spec.ts covers the day-sheet ordering, the cancelled filter and the date range.
  • api/test/integration/visits.integration-spec.ts is the real evidence, with twenty racers against a live Postgres: one window goes to exactly one of twenty; a queue of people take one window each; a taken window stops being offered; a cancelled window goes back on offer and is raced again, asserting one live row and two rows in total at that start, which is precisely what the partial index promises; and an off-grid window is refused however hard it is pushed.
  • frontend/src/features/visits/types.test.ts and frontend/src/features/admin/visits/types.test.ts cover the pure day, window and filter helpers; VisitDayStrip, VisitWindowPicker, VisitForm and the console table have stories.
  • Gap: frontend/scripts/browser-flows.sh has no visit flow. flow_contact opens /contact and drives only the contact form, so the booking UI on that same page is never exercised in a browser, and neither features/reach-the-studio.md nor features/open-studio.md covers it.

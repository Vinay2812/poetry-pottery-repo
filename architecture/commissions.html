Commissions and reference photos

Two paths let a customer ask for a piece that does not exist yet. A made-to-order product on the shelf takes option choices and up to three reference photos, priced and hashed into a cart line. A commission brief on /custom takes no product at all: a piece type, a size, a glaze, an optional line to carve, and the same three photos, filed as a row the studio works through in four states. Both share one uploader, which presigns straight into a per-customer folder and is the one image path in the system that never goes through the confirmation ledger.

Architecture

How it works

The uploader

api/src/storage/storage.resolver.ts:StorageResolver.createCustomizationUpload is @AuthRequired() and @StrictThrottle(), so five presigns a minute per signed-in caller. It takes content_type and size only; the filename is synthesised. Its own allowlist, REFERENCE_PHOTO_TYPES, is narrower than the storage service's: JPEG, PNG and WebP, with AVIF deliberately left out, and a miss is Reference photos must be JPEG, PNG or WebP. It then calls StorageService.createImageUpload with folder: "customization", subfolder: String(user.db_user_id) and filename: reference.<ext>, so a key reads customization/<userId>/<epochMs>-<8 hex>-reference.jpg and one customer's photos are namespaced away from another's.

This path sits outside the UploadPurpose system entirely. There is no CUSTOMIZATION member, no confirmUpload call, no sharp read-back, no confirmed_uploads row and no assertConfirmed at save time. Dimensions and ratio are never checked server side. The only server-side guarantee is StorageService.isOwnUrl(url), a prefix match on the public bucket URL, which means any key in the bucket would pass. See the storage page for the path admin images take instead.

In the browser, frontend/src/features/products/hooks.ts:useReferencePhotos owns the whole lifecycle. It presigns, then PUTs through putWithProgress, a raw XMLHttpRequest rather than fetch, because fetch reports no upload progress. Preview object URLs are tracked in a useRef(new Set()) and revoked on removal, on clear and on unmount. frontend/src/features/products/types.ts holds the client mirror: MAX_REFERENCE_PHOTOS = 3, MAX_REFERENCE_PHOTO_BYTES of 8 MB, the same three MIME types, validateReferencePhoto, remainingReferenceSlots, toConfirmedPhotoUrls and isPhotoUploadPending, under a comment saying plainly that the API repeats every one of these and this only saves a round trip.

Photos on a cart line

api/src/features/cart/selections.ts gained two things alongside the option resolver described on the product options page.

  • resolveReferenceImages(urls, isOwnUrl) trims, drops blanks, de-duplicates through a Set, enforces MAX_REFERENCE_IMAGES = 3 with Attach up to 3 reference photos, and rejects a foreign URL with That reference photo was not uploaded.
  • selectionKey(selections, referenceImageUrls = []) now hashes both. The canonical form is a two-element array: the selections sorted by group_id and mapped to [group_id, option_id, text], then the photo URLs sorted. An empty selection set and an empty photo list still returns "", the column default, so plain lines keep merging. Two identical option sets with different photos are two different lines; the same photos in a different order are one.

CartService.add resolves both only when the product is is_customizable, and silently drops whatever a client sent for a piece that is not. The rest of the add path is unchanged: the two-integer advisory lock, the merge, the clamp at ten, and the upsert on @@unique([user_id, product_id, selection_key]).

The stored shape, and the row that predates it

ProductCustomisation is not a Prisma model. It is an ambient TypeScript interface in api/src/types/prisma-json.d.ts describing the JSON in cart_items.selections and order_items.selections:

api/src/types/prisma-json.d.ts. The Prisma columns are annotated /// [ProductSelections].
TypeShape
ProductSelectiongroup_id, group_name, option_id, option_name, text, price_modifier
ProductCustomisation{ options: ProductSelection[]; reference_image_urls: string[] }
ProductSelectionsProductSelection[] | ProductCustomisation

The union is the migration. Rows written before reference photos existed hold a bare option array, and readCustomisation(stored) normalises both into { options, reference_image_urls } on every read, so no backfill was needed and no reader has to know which era a row came from.

The order snapshot

OrdersService.place writes each line's selections in the new object shape: { options: item.selections, reference_image_urls: item.reference_image_urls }, beside the frozen product_name, product_image, unit_price, quantity and line_total. Each option entry carries its own group_name, option_name and price_modifier, so renaming a group or repricing an option later cannot rewrite what the customer ordered. The read side, toOrder(row, now), runs readCustomisation per item and splits it back into selections and reference_image_urls; the admin orders service imports and calls the same function rather than keeping its own mapper.

Mails that carry the photos

  • api/src/mail/templates/orders.ts:referenceLinks(order) flat-maps every item's photo URLs into labelled links, <piece> — photo N, and referenceBlock wraps them under a "Reference photos" heading, returning an empty array when there are none.
  • That block is rendered into exactly two mails, orderPlacedCustomerMail and orderPlacedStudioMail, immediately after the pieces list. orderStatusMail and orderStudioNoteMail do not carry it.
  • api/src/mail/templates/commissions.ts:commissionStudioMail emits its own "Reference photos" block. commissionAcknowledgementMail does not: the customer gets the brief back plus the request id, not their own photos.

The commission brief

CommissionRequest is a real model, @@map("commission_requests"), keyed on nanoid(12): piece_type, size, glaze, carved_words, notes, name, email, phone, reference_image_urls String[], is_read, status, a nullable user_id with onDelete: SetNull, and created_at. There is no updated_at. Indexes cover (is_read, created_at), (status, created_at) and user_id.

Two migrations built it: 20260917110000_commission_requests creates the table (and, in the same file, adds products.is_commission), and 20260917130000_commission_status adds the enum and the column additively, so every brief already filed starts where it stood.

Submitting a brief

  1. createCommissionRequest carries no guard and @StrictThrottle(). It calls authGuard.tryAuthenticate(context.req) and passes user?.db_user_id ?? null, so anyone can brief a piece and a signed-in visitor gets theirs filed against their account. Anonymous callers are throttled by IP rather than by user.
  2. parseCommissionInput is a zod schema surfacing only the first issue: piece_type 2 to 60, size and glaze 1 to 60, carved_words at most MAX_CARVED_WORDS = 40 because the line is cut into wet clay by hand, notes at most 1000, name 2 to 80, a lowercased email, a phone through the shared normalisePhone, and at most three URLs.
  3. CommissionsService.create then runs its own origin check, Reference photos must be uploaded through the studio, and creates the row. There is no transaction.
  4. After the write it enqueues commissionStudioMail to env.BUSINESS_EMAIL when that is set, and commissionAcknowledgementMail to the briefer unconditionally. Both are awaited before the mutation returns, so unlike the order path a queue failure fails a mutation whose row is already committed.

A signed-out visitor can file a brief but cannot attach photos, because the presign is @AuthRequired(). CommissionBriefContainer reads useAuth() and, when signed out, swaps the picker for a line offering WhatsApp instead. That asymmetry is deliberate but it is the one place the two halves of the form disagree about who may use them.

What the form offers

commissionOptions is public and unguarded, behind redis.getOrSet("commissions:options", 120, ...). It never invents a choice: piece_types are categories that have at least one sellable product, sizes are active ProductOption rows whose group is named "size" or "sizes" case-insensitively, and glazes are the distinct Product.color_name values of sellable pieces. All three run through a local unique() that trims and drops blanks.

The glaze list on the brief form reads color_name, not the Glaze model that the catalogue facet uses. The two can disagree. CommissionsService.invalidateOptionsCache() exists but is never called from anywhere, so the only thing that refreshes this list after an admin edit is the 120 second TTL.

is_commission and the /custom page

commissionPieces(limit = 6) clamps to MAX_COMMISSION_PIECES = 12 and shows past work: products flagged is_commission, newest first, falling back to the made-to-order shelf when the studio has flagged none yet. The flag is set through createProduct and updateProduct (a tri-state partial update) and exposed as a non-null Boolean on Product.

is_commission has no effect on availability or the catalogue. sellableProductWhere, availableProductWhere and archivedProductWhere are built only from is_active, the collection window, stock and is_customizable. A flagged piece stays fully purchasable and still appears on the shelf, in search and in the archive. Its one reader is CommissionsService.pieces(), and that branch does not apply the sellable predicate, so an inactive piece flagged as past work still shows on /custom.

app/(storefront)/custom/page.tsx is a server component that awaits getCommissionOptions(), getCommissionPieces(6) and getSiteSettings() together, both catalogue loaders falling back to empty, and renders CommissionSteps, the past-work grid when there is one, and CommissionBriefContainer.

The studio's inbox

The three admin fields are @AdminRequired() methods on CommissionsResolver itself rather than a separate admin module: commissionRequests(filter), markCommissionRequestRead(id) and setCommissionRequestStatus(id, status). The list filters by status, by the tri-state read flag and by a case-insensitive search across name, email and piece type, newest first. Both writes route a missing row through rethrowMissing("Commission request not found").

One rule is shared by both halves: moving a brief off NEW marks it read, because somebody must have looked at it. The service writes { status, ...(status === NEW ? {} : { is_read: true }) } and the console's reducer applyCommissionPatch mirrors exactly that, including leaving the unread mark alone when a brief is put back to NEW. CommissionsContainer also marks a brief read simply by opening its drawer.

The admin inbox module, api/src/features/admin/inbox, covers contact messages, newsletter subscribers and restock watchers. It does not touch commissions, despite the console route being called the commission inbox.

Edge cases and failure handling

  • Reference photos are never verified. No sharp decode, no dimension or ratio rule, no ledger row, and isOwnUrl is a prefix match, so any key in the bucket is accepted. The mitigations are the per-user subfolder, the strict throttle and the three-photo cap.
  • Nothing deletes an abandoned reference photo. Unlike review photos, which are parked in Redis and swept into the storage.delete-object job, a presigned customisation key that never reaches a cart line stays in the bucket for good.
  • Photos fork a cart line. Because they are inside selectionKey, adding the same piece twice with different photos leaves two lines rather than a quantity of two.
  • A non-customisable product silently drops both selections and photos rather than rejecting the request.
  • Legacy cart and order rows hold a bare array, which is why every reader goes through readCustomisation instead of reading the column directly.
  • A signed-out brief cannot carry photos, and the form says so rather than failing at submit.
  • A commission mail failure fails the mutation, after the row has already been written, because both enqueues are awaited outside any transaction.
  • The options list can go stale for two minutes, and the invalidation helper that would fix that is never called.
  • An inactive piece flagged is_commission still appears on /custom, because that branch skips the sellable predicate.
  • Three separate constants say three. MAX_REFERENCE_IMAGES in the cart, MAX_REFERENCE_PHOTOS in the commission service and a third copy in the frontend all happen to agree; nothing keeps them in step.

Tests

  • api/src/features/cart/selections.spec.ts covers resolveReferenceImages (trim, blank, de-duplicate, over the cap, foreign URL), that selectionKey separates lines by photo set but ignores photo order, and that readCustomisation reads legacy arrays, the new object shape and empty rows.
  • api/src/features/cart/cart.service.spec.ts asserts the exact upsert payload for a custom line with a photo, and that a foreign URL rejects.
  • api/src/features/commissions/commissions.service.spec.ts covers twelve cases: the normalised brief and its acknowledgement, the studio mail only when BUSINESS_EMAIL is set, foreign and over-cap photos, carved words longer than the rim can hold, blank words and notes treated as absent, the options query offering only what the shelf carries, pieces() preferring flagged rows and falling back to the made-to-order shelf, inbox filtering and paging, and a brief counting as read once it leaves NEW.
  • api/src/features/commissions/commissions.resolver.spec.ts covers the optional-auth wiring both ways and asserts the guard metadata per field: none on the three public ones, AdminGuard on the three console ones.
  • api/src/mail/templates/orders.spec.ts covers the reference block being linked for both recipients and omitted when nothing is attached.
  • Frontend: frontend/src/features/products/types.test.ts covers validateReferencePhoto and remainingReferenceSlots; frontend/src/features/commissions/types.test.ts covers the step order, toCommissionInput, the WhatsApp fallback and the brief summary; frontend/src/features/admin/commissions/types.test.ts covers the row mapper, the status tone, the phone link and applyCommissionPatch including the "off NEW means read" rule.
  • Gaps: there is no integration spec for commissions, no test renders either commission mail template, and StorageResolver.createCustomizationUpload has no spec at all, so its narrower MIME allowlist and its guard stack are untested.

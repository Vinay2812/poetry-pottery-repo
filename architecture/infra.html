Infra and environments

Local infrastructure is three containers on one compose network: Postgres 17 with pgvector baked in, Redis 8 and RabbitMQ 4. Both applications validate their environment with zod at import time and exit with a per-variable report rather than failing later, and every optional dependency - R2, SMTP, Sentry, and to a degree Redis and RabbitMQ - degrades to a logged no-op instead of stopping the process.

infra/docker/initdb/01-extensions.sql is a single CREATE EXTENSION IF NOT EXISTS vector;, run once on a fresh data volume. docker-compose.api.yml includes the database file and adds the containerised API, built from infra/docker/Dockerfile.api with api/ as the build context. It loads env_file: ../../api/.env for the application values and then overrides the in-network endpoints in an environment: block, pointing DATABASE_URL at postgres:5432, REDIS_URL at redis:6379 and RABBITMQ_URL at rabbitmq:5672, and it waits on all three health checks.

The README says the compose environment: block also pins NODE_ENV=production and PORT. In the compose file it does not: NODE_ENV=production comes from the Dockerfile's ENV and PORT comes from api/.env or the schema default.

The image

Dockerfile.api is three stages on node:24-alpine. The build stage installs with a frozen lockfile behind a BuildKit cache mount on the pnpm store, runs prisma generate with a dummy DATABASE_URL (because prisma.config.ts resolves the variable eagerly while never connecting), builds with Nest, and then prunes to production dependencies in place so the generated Prisma client inside the store survives. The runner stage copies the pruned modules and the build output as the node user, creates the model cache directory, exposes 6060 and declares a HEALTHCHECK that wgets /health. The image contains no real configuration; everything real arrives at runtime.

Three ways env reaches a container

  1. Compose interpolation (${VAR:-default}), resolved when you run docker compose up. Compose auto-loads infra/docker/.env because it sits next to the compose files, and a shell variable outranks it. That file holds only ports and database credentials.
  2. Container runtime env, from env_file: ../../api/.env so application values live in one place whether you run pnpm dev or the container, with the environment: block overriding the values that must differ inside the network. Precedence is environment over env_file over the image's ENV.
  3. Build-time env, of which there is none beyond the dummy DATABASE_URL.

Validation

api/src/config/env.ts calls loadDotEnv() at import time, which uses process.loadEnvFile so existing process.env values win, then parses with zod. A failure writes Invalid environment configuration: followed by one line per issue to stderr and calls process.exit(1): fail fast at import, not at boot. buildEnv adds the derived LOG_LEVEL and the three environment flags.

LEGACY_DATABASE_URL is deliberately not in the schema. Only api/scripts/import-legacy.ts reads it, straight off process.env, and api/.env.example documents it as a comment.

The frontend splits its schema. clientEnv is parsed eagerly from static process.env.NEXT_PUBLIC_* references so Next can inline them: NEXT_PUBLIC_API_URL, NEXT_PUBLIC_CLERK_PUBLISHABLE_KEY and NEXT_PUBLIC_LOG_LEVEL. getServerEnv() validates CLERK_SECRET_KEY and LOG_LEVEL, throws if called in the browser and memoises. Frontend failures throw rather than exiting.

frontend/.env.example is not in the repository: frontend/.gitignore has a blanket .env* rule that ignores it, while both READMEs tell you to copy it. The API's api/.env.example is committed because the root ignore file lists only .env, .env.local and .env.*.local.

Ports

Frontend 3030, API 6060, Postgres 5433 mapped to 5432, Redis 6381 mapped to 6379, RabbitMQ 5672 with the management UI on 15672, Storybook 6006. Redis sits on 6381 because 6379 and 6380 are taken by other local projects.

Boot order

  1. import "./instrument" is the first line of main.ts, so Sentry initialises before anything else - and only when SENTRY_DSN is set, with a trace sample rate of 0.1 in production and 1 elsewhere.
  2. NestFactory.create with a winston logger supplied up front, so boot problems such as an unreachable broker are not buffered.
  3. helmet, relaxed in development so Apollo Sandbox loads.
  4. trust proxy, CORS, the Clerk middleware, shutdown hooks and listen.

app.module.ts imports everything exported from src/modules.ts, registers the throttler guard and the exception filter globally, and applies the request id middleware to every route. src/modules.ts is the single registry: the config module with Nest's own env loading turned off, winston, the Redis-backed throttler, the Apollo GraphQL module and the re-exports of every infrastructure and feature module. src/resolvers.ts is a flat list of 14 storefront and 12 admin resolvers, and it is what defines the emitted schema surface - a resolver missing from it is silently absent.

GraphQL module configuration

  • autoSchemaFile writes schema.gql in development and stays in memory in production, because the container runs as a non-root user with a read-only application directory.
  • sortSchema: true, playground: false, stack traces only outside production.
  • introspection: true globally, because Sandbox needs it, with production access narrowed per request by the introspection plugin.
  • The context factory is ({ req, res }) => ({ req, res }), which is what lets guards, the throttler and the logging plugin all reach the Express request.

Introspection gating

api/src/common/graphql/introspection.plugin.ts has three parts. isIntrospectionDocument visits the parsed AST looking for a field named __schema or __type, so a renamed introspection query is still caught. shouldRejectIntrospection returns false immediately outside production or for a non-introspection document, and otherwise compares the provided key against env.SCHEMA_SYNC_KEY. createIntrospectionGuard hooks didResolveOperation, reads the x-schema-key header and throws a FORBIDDEN GraphQL error when rejected. That header is exactly what frontend/codegen.ts sends.

Health, request ids, errors and logs

  • GET /health runs three Terminus indicators in parallel: prisma.$queryRaw\SELECT 1\`, redis.client.ping() and a synchronous check of the AMQP connection flag. It carries @SkipThrottle({ default: true, short: true, strict: true })`, because the bare decorator only skips the default profile.
  • RequestIdMiddleware reuses an incoming x-request-id or generates a UUID, sets it on the request and the response and logs the method and URL.
  • AllExceptionsFilter catches everything, logs at error with a stack and reports to Sentry at 500 and above and at warn below that, returns the original HttpException for GraphQL hosts (so the UNAUTHENTICATED and FORBIDDEN messages survive) and a generic internal error otherwise, and writes { statusCode, message, requestId, timestamp } for HTTP hosts.
  • The GraphQL logging plugin logs one line in and one line out with the request id, the database user id, the duration and the error count. Variables and response payloads are logged outside production only, and IntrospectionQuery is skipped so Sandbox polling does not flood the log.
  • createWinstonOptions() is silent under test, JSON in production and pretty Nest-style in development.

Redis

Two consumers: RedisService.getOrSet for the settings, content and catalogue caches, and ThrottlerStorageRedisService wrapping the same client so rate limit counters hold across replicas. The client is lazy with maxRetriesPerRequest: 2 and no offline queue, connection failure at boot is logged rather than fatal, and every cache operation swallows its error and degrades to the loader.

  2. api/src/config/env.ts:loadEnvRuns at import: loadDotEnv(), zod parse, and process.exit(1) with a per-issue report on failure.

  4. api/src/app.module.ts:AppModuleImports every module from modules.ts; registers GqlThrottlerGuard as APP_GUARD and AllExceptionsFilter as APP_FILTER.
  5. api/src/modules.ts:CustomThrottlerModuleInjects RedisService and builds the three named profiles over Redis storage, or memory under test.
  6. api/src/modules.ts:CustomGraphQLModuleApollo driver with the introspection guard and the logging plugin.

How codegen reaches the schema

  1. frontend/codegen.tsLoads .env.local then .env, reads SCHEMA_URL and SCHEMA_SYNC_KEY.
  2. api/src/common/graphql/introspection.plugin.ts:createIntrospectionGuardAllows the introspection document because the x-schema-key header matches.
  3. api/scripts/emit-schema.tsThe offline path: boots only the schema builder module over src/resolvers.ts and writes api/schema.gql with a fixed banner.
  4. scripts/check-schema-sync.shThe pre-push hook re-emits, regenerates from the file rather than a server, and typechecks.

Edge cases and failure handling

  • Redis down: caches degrade to the loader, throttling fails open, and /health reports it.
  • RabbitMQ down: boot still succeeds, publishing logs and drops, and /health reports queue: down, which fails the whole result.
  • SMTP unset: mail is logged as skipped and acked, which is the local development path.
  • R2 unset: uploads are disabled and, importantly, assertConfirmed becomes a no-op.
  • Sentry unset: the instrument module does nothing.
  • A bad environment value stops the API at import with a per-issue report rather than failing somewhere later.
  • pgvector is per database, which is why the integration runner creates a whole throwaway database rather than a schema.
  • A resolver missing from src/resolvers.ts is silently absent from the emitted schema, even though it works at runtime.
  • frontend/.env.example is ignored by git, so a new checkout has nothing to copy despite the instructions.

Tests

  • api/src/config/env.spec.ts asserts the documented defaults, comma separated parsing with stray whitespace and a trailing comma, a blank DSN meaning disabled, rejection of a missing or non-URL DATABASE_URL and of invalid enum and numeric values, the three LOG_LEVEL derivations, the environment flags, and that buildEnv({}) throws.
  • api/src/common/graphql/introspection.plugin.spec.ts covers the AST detection and the key comparison; api/src/common/graphql/logging.plugin.spec.ts covers the log line contents.
  • api/src/redis/redis.service.spec.ts covers getOrSet and reviveDates; api/src/prisma/prisma.service.spec.ts covers the ambient transaction machinery.
  • api/test/app.e2e-spec.ts boots the whole application module with Prisma, Redis and the queue mocked and asserts that /health reports the database up, that x-request-id comes back as a string, and that an unauthenticated admin query returns Authentication required with code UNAUTHENTICATED.

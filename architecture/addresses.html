Addresses

The address book is small but it carries one invariant that everything downstream relies on: a user has at most one default address and at least one whenever they have any addresses at all. Creation, editing, deletion and explicit promotion each enforce it inside a transaction, ownership is checked by scoping every lookup to the signed-in user, and orders never reference an address row - they snapshot it as JSON, so editing or deleting an address can never rewrite history.

Architecture

How it works

Validation

address-validation.ts:parseAddressInput runs a zod safeParse and throws BadRequestException(result.error.issues[0]?.message ?? "Check the address details"), so the customer sees one human-worded problem at a time rather than a list. The rules: name 2 to 80, line1 3 to 120, city and state 2 to 60, all trimmed; line2 and landmark trimmed to 120 with blank becoming null; pincode must match /^\d{6}$/; a nullish is_default becomes false.

normalisePhone strips spaces and hyphens and matches /^(?:\+?91|0)?(\d{10})$/, returning just the ten digits or null, which becomes Enter a valid 10-digit phone number. The storage invariant is exactly ten digits with no country code. It is shared rather than copied: the contact form, the commission brief and the studio visit booking all import it from here.

The default-address invariant

  • create counts the user's existing addresses inside a transaction and sets isDefault = fields.is_default || existing === 0, so the first address is always the default. When it is the default, clearDefaults(userId) runs first.
  • update computes isDefault = fields.is_default || existing.is_default, so editing the current default never un-defaults it. clearDefaults(userId, id) excludes the row being written.
  • remove deletes, returns early when the deleted row was not the default, and otherwise promotes the newest remaining address. If none remains, nothing happens. It always returns true.
  • setDefault clears the others and then sets the flag.
  • clearDefaults(userId, exceptId?) is an updateMany over rows that are currently default, optionally excluding one id.

list orders by is_default desc then created_at desc, and toAddress projects only the client-visible columns, dropping user_id and the timestamps.

Ownership

Every write goes through findOwned, a lookup scoped by both id and user_id that raises NotFoundException("Address not found") on a miss. That is the cross-tenant guard: another user's address is indistinguishable from one that does not exist.

Addresses and orders

An order never references an address row. place copies the fields into Order.shipping_address as JSON, so deleting or editing an address never mutates order history.

The client

  • useAddresses reads with cache-and-network then cache-first and sorts default first.
  • useAddressMutations wraps each mutation in try-catch with refetchQueries: ["Addresses"], awaitRefetchQueries: true, so the awaited refetch is the baseline, and toasts both success and failure.
  • useAddressBook adds useOptimistic(addresses, applyAddressAction) for delete and set-default only. Create and update are not optimistic, because a new row has no id until the server gives one.
  • The reducers in frontend/src/features/addresses/types.ts mirror the service: withDefaultOn keeps one default and re-sorts, afterDelete promotes the first remaining row only when the deleted one was the default.
  • AddressPickerContainer watches hasSelection and calls onSelect(toPreferredAddressId(addresses)) when the selected address disappears or on first load, so deleting the selected address clears checkout's addressId instead of pointing at a dead row.

Edge cases and failure handling

  • The first address is always the default, whatever the flag says.
  • Editing the current default cannot clear the flag by omitting it.
  • Deleting the default promotes the newest remaining address; deleting a non-default promotes nothing.
  • Another user's address is a 404, never a 403, so ids cannot be probed.
  • There is no partial unique index on (user_id, is_default). Two concurrent setDefault calls under read committed could in principle leave two defaults. It degrades gracefully because the list is ordered default first and toPreferredAddressId takes the first. Studio visits show what the alternative looks like: one partial unique index and a caught P2002 in place of an invariant held in application code.
  • Deleting an address never touches order history, because orders hold a JSON snapshot.
  • Only the first validation issue is surfaced, by design.

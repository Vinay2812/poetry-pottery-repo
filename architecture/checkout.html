Checkout and orders

Checkout is one transaction with a strict internal order. It starts by taking the cart's product rows with FOR UPDATE in id order, which pins prices and availability and makes deadlocks impossible; it re-quotes from that same snapshot so the page and the order agree; it takes stock only through a conditional decrement that cannot oversell; it redeems a coupon through a conditional increment that cannot double spend; and it writes an order whose totals, address and line details are permanent snapshots. Afterwards every status change, whether a customer cancel or an admin move, goes through one guarded state machine, and the same machine is what decides when stock goes back on the shelf and the waiting list is told.

Architecture

How it works

The quote

OrdersService.quote(userId, couponCode, snapshot?) takes an optional cart snapshot. When place passes one, the cart is not re-read, so the totals shown and the lines written come from one identical object. It splits the lines into available and unavailable, turns the unavailable ones into problems strings of the form "<name>: <reason>", sums the available line totals, and then applies the coupon.

api/src/features/orders/coupons.ts:checkCoupon.

couponDiscount floors a percentage (Math.floor(subtotal * value / 100)) or takes the fixed value, then clamps to [0, subtotal]. Money is whole rupees end to end, so a discount is never negative and never exceeds the subtotal; the total can fall to the shipping fee but never below zero. A bad code never throws in quote: it comes back as a coupon_message with coupon_code still null. A valid code worth zero rupees stays applied rather than being rejected.

Shipping is computed on the discounted subtotal in quote, while CartService.get computes it on the undiscounted one, so a coupon can push a cart back under the free shipping threshold.

Placing an order

Everything below happens inside a single prisma.withTransaction, in this order.

  1. Lock the product rows. lockCartProducts(userId) runs SELECT id FROM products WHERE id IN (SELECT product_id FROM cart_items WHERE user_id = $1) ORDER BY id FOR UPDATE. The ORDER BY id is the deadlock-avoidance invariant: two carts holding the same pieces always take the locks in the same order. Holding the rows pins price, is_active and option state for the whole transaction.
  2. Find the address, scoped by user_id.
  3. Read the cart, after the locks, so availability and prices are the locked ones.
  4. Quote from that snapshot, so the checkout page and the order agree.
  5. Guards, in this deliberate order: no address raises Choose a delivery address; any problems raises Some pieces are no longer available: ... naming the pieces, so a cart whose only line just sold out is not misreported as empty; only then does an empty available set raise Your cart is empty; finally a code that failed validation raises its own message, because an invalid code fails the order rather than being silently dropped.
  6. Take the stock. Made-to-order pieces only increment sales_count. Everything else goes through the conditional decrement: product.updateMany({ where: { id, stock: { gte: quantity } }, data: { stock: { decrement }, sales_count: { increment } } }), and taken.count === 0 raises <name> sold out while you were checking out, which rolls the whole transaction back including every earlier decrement.
  7. Redeem the coupon, if any, with a conditional increment: updateMany where the coupon is active and either max_uses is null or uses_count < max_uses. A zero count raises That code has been fully redeemed. This is the single-use guard.
  8. Create the order with id: newPublicId("PP") and denormalised snapshots: the four money fields from the quote, the shipping address copied field by field into JSON, the gift fields from readGift, and per line the product name, first image, unit price, quantity, line total and the customisation object { options, reference_image_urls }.
  9. Clear only the available cart lines. Unavailable lines stay, although the guards mean you cannot reach this point with any.

newPublicId("PP") builds a ten-character nanoid over the alphabet 23456789ABCDEFGHJKMNPQRSTUVWXYZ, which has no vowels or look-alike characters so an id reads cleanly over WhatsApp or the phone. Orders are PP-, events EV- and workshop bookings WS-.

  • STOCK_HOLDING is every status except the two terminal ones, so stock is released exactly when an order enters CANCELLED or REFUNDED.
  • STATUS_TIMESTAMP maps each non-pending status to its *_at column.

Gifts

PlaceOrderInput carries two nullable extras, gift_note and hide_prices, normalised before the transaction opens by api/src/features/orders/gift.ts:readGift(note, hidePrices). The note is trimmed and cut to GIFT_NOTE_MAX_LENGTH = 200, the length of a card. An order counts as a gift when there is a note or the hide flag is set, and hide_prices is only stored as true on an order that is a gift, so the flag can never be set on its own by a client that forgot the note.

  • On the client, toGiftView(isGift, note, hasHiddenPrices) returns nulls outright once the gift box is unticked, so an abandoned draft note never leaks into the mutation.
  • The shopper's order page renders a "Sent as a gift" block with the note in the script face and one line saying whether the packing slip goes in with or without prices.
  • The console shows describeGiftHandling, which names both jobs, whichever single job there is, or says plainly that it is not a gift.
  • The packing slip honours the flag. PackingSlip drops the unit and line columns and the whole totals list when isPricesHidden, and prints the gift note as its own section.
  • giftBlock is spread into orderPlacedStudioMail only. The customer's own confirmation says nothing about the gift, which is the point: it is the studio that has to write the card.

Care lines

There is no care model either. toCareLines(pieces) in api/src/features/orders/care.ts flattens every ordered piece's care_notes into one list for the whole parcel, in purchase order, de-duplicating case-insensitively and dropping blanks, and toOrder attaches it as Order.care_notes.

The API returns that on every order whatever its status; the delivered gate lives in the two consumers. toDeliveredCareLines(status, careNotes) returns an empty list unless the status is DELIVERED, which is what makes OrderCareGuide appear on the order page, and orderStatusMail spreads careBlock(order) only for DELIVERED, with a link on to /care. The packing slip prints the care section unconditionally, because it travels in the box.

Studio notes

OrderNote is a line the studio writes to the customer about their order, with an optional photo: order_id, body, image_url, created_at, indexed on (order_id, created_at) and cascading from the order. orderInclude pulls them oldest first and toOrder exposes them as Order.studio_notes.

addOrderNote(input) is @AdminRequired() but lives on the storefront OrdersResolver rather than in the admin module, which is where the write side sits for historical reasons the source comment records. OrdersService.addNote:

  1. Trims the body and cuts it at STUDIO_NOTE_MAX_LENGTH; empty is Write something for the customer.
  2. storage.isOwnUrl(imageUrl), else Attach a photo uploaded to the studio.
  3. uploads.assertConfirmed([imageUrl], [], UploadPurpose.ORDER_NOTE), so unlike a reference photo a studio note photo is held to the 4:3, 1200 by 900 spec on the storage page.
  4. Creates the row, re-reads the order, and enqueues orderStudioNoteMail to the customer straight away. There is no transaction and no job of its own; the note is written for the customer, so it goes out as one mail.

Do not confuse this with setOrderAdminNote, which writes the private Order.admin_note and mails nobody.

The dispatch window

Two settings columns, dispatch_days_min and dispatch_days_max, default 7 and 12, read through the same settings:site Redis key with its 60 second TTL as the shipping fee. assertDispatchDays(min, max) in the admin content service refuses non-integers and anything below one (Dispatch days must be whole days), a reversed pair, and anything past 120 days, and it checks a one-sided edit against the stored other end so a partial patch cannot invert the window.

The shopper sees it through toArrivalWindow(placedAt, min, max), which counts both ends from created_at, clamps so a reversed settings row still reads forwards, and formats in Asia/Kolkata as either Should reach you between <d1> and <d2> or Should reach you around <d>. It renders only inside OrderPlacedBanner, that is, on the order page immediately after placement.

The product page's own "Ships in" fact row does not read these settings: toFactRows hard-codes About ten days for a made-to-order piece and Three working days for everything else. The console's preview line, describeDispatchWindow, describes the settings and not that row.

applyStatus, the shared transition

applyStatus(current, next, extra) refuses an illegal edge up front, then inside a transaction runs a status-predicated conditional update: order.updateMany({ where: { id, status: current.status }, data: { status: next, [stamp]: now, ...extra } }). A zero count raises ConflictException("This order was just updated, refresh and try again"), which is what makes it impossible for two concurrent transitions to both win, and therefore impossible to release stock twice.

When the transition releases stock, each line increments sales_count back down and, for non-customisable pieces, increments stock back up, selecting the new stock back so cameBackInStock(restored.stock - item.quantity, restored.stock) can decide whether that piece just reappeared on an empty shelf. Those ids collect in a local array inside the transaction and are announced through announceRestock only after the commit, so a rolled-back cancellation never wakes a waiting list; see the notifications page. When the order carried a coupon, coupon.updateMany({ where: { id, uses_count: { gt: 0 } }, data: { uses_count: { decrement: 1 } } }) gives the use back without letting the counter go negative. The admin cancel path routes through the same function, so stock and coupon uses come back identically however the cancel was initiated.

Mails

notifyPlaced runs after the transaction commits: the customer mail always, and orderPlacedStudioMail to env.BUSINESS_EMAIL when it is set. notifyStatus runs after cancel and after every admin transition; orderStatusMail returns null for PENDING, so no mail goes out for it. Both go through MailService.enqueue, which publishes a mail.send job, so SMTP latency never blocks the mutation. Enqueuing after commit means a crash in the gap loses the mail but not the order; there is no outbox.

Reading orders back

toOrder decides whether a line still links back to the shop: isLinkable requires product.is_active and a collection that has not ended, otherwise item.product is null and the UI falls back to the snapshotted name and image. In the schema Order.coupon is onDelete: SetNull and OrderItem.product is onDelete: Restrict, so a product that has ever been ordered cannot be hard deleted and archiving is the only retirement path.

The client

  • CheckoutContainer keeps appliedCoupon in state and wraps it in the reducer-free form useOptimistic(appliedCoupon) plus a transition, so an entered code renders as pending without inventing a discount. toCouponView derives isSettled from code === quoteCode, and the discount is shown only once settled.
  • Applying a code refetches the quote and only then commits setAppliedCoupon; a rejected code toasts the server's message and refetches again with the previous code to restore the server state. startCouponTransition wraps the transition in try-catch so a failed refetch ends in a toast rather than in the route's error boundary.
  • The quote query is fetchPolicy: "network-only", because prices and stock move.
  • Placing the order is not optimistic at all. It sends quote.coupon_code, the server-validated code, never the draft, and on success pushes to the order page with ?placed=1.
  • blockedReason is ordered: no address, then an empty available set, then unavailable pieces. Totals render quote?.x ?? cart?.x ?? 0 so the page never blanks while a quote is in flight.
  • OrderDetailContainer uses useOptimistic(order, applyOrderCancellation); useCancelOrder runs the mutation with no refetch, because the reply is the whole Order and Apollo's own normalisation is the new baseline.
  • The orders list keeps page in local state and renders the previous page dimmed with aria-busy while the next one loads, rather than swapping in skeletons.

Edge cases and failure handling

  • Oversell is prevented by the conditional decrement, not by the read. Under the FOR UPDATE locks the decrement never even contends.
  • A partial take is impossible: any line that fails aborts the transaction and rolls back the earlier decrements.
  • Double cancel cannot credit stock twice, because the status-predicated update means only one transition wins and the loser gets a conflict.
  • A coupon cannot be spent twice, because redemption is a conditional increment, and cancelling gives the use back through a uses_count > 0 guarded decrement.
  • A price changed mid-checkout is honoured as of the commit: the integration spec proves an order prices at the new value when a concurrent writer commits while place is blocked on the row lock.
  • A piece retired mid-checkout rejects the order with no longer available and leaves the other product's stock untouched.
  • Mail is enqueued after commit, so a crash between the two loses the mail but not the order, and a broker outage logs and drops the job rather than failing the mutation.
  • An invalid coupon fails the order rather than being dropped, so the customer never pays a total they did not see.
  • Order history is immutable. Totals, the address and the line snapshots do not change afterwards, and the shop link is dropped once the piece is archived. Studio notes are the one thing that accumulates on an order after the fact, and only an admin can add one.
  • The hide-prices flag cannot be set without the order being a gift, because readGift derives isGift first and gates the flag on it.
  • Care lines are on the payload of every order; only the page and the mail hold them back until delivery, and the packing slip prints them whatever the status.
  • A studio note mail failure fails the mutation after the note row is committed, because the enqueue is awaited outside any transaction.
  • The dispatch window can lag an admin change by 60 seconds, like every other site setting.

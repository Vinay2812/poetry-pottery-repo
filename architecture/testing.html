Testing and verification

Verification has three layers. Unit specs cover the pure logic and the services with their edges mocked. Integration specs run the real services against a real Postgres created and dropped per run, and exist specifically to prove the concurrency guards: eighteen race tests, each with twenty simultaneous callers. Storybook runs every presentational component in a real browser with accessibility violations failing the build. On top of that sit three git hooks, of which the important one refuses a push whose GraphQL schema and generated hooks have drifted apart.

The integration runner

pnpm -C api test:integration runs api/test/integration/run.ts, which does the following.

  1. loadDotEnv() reads api/.env.
  2. It requires DATABASE_URL with the message DATABASE_URL must point at the compose Postgres. The script starts nothing: the compose stack must already be up.
  3. It generates a sandbox name it_<random hex> and swaps it into the URL path.
  4. It creates that database over a raw pg client. A whole database rather than a second schema, because pgvector is installed per database, so the initial migration's vector(384) columns could not live in another schema.
  5. It runs prisma migrate deploy against the sandbox, so the real migrations are exercised.
  6. It runs vitest with the integration config.
  7. In a finally, it drops the database with WITH (FORCE).

api/test/integration/harness.ts builds a testing module with the real settings, cart, orders, events and workshops services and a real PrismaService wrapped in withAmbientTransactions, stubbing only the outside world: Redis (whose getOrSet calls the loader directly), mail and search. resetData truncates 19 tables in foreign key order with RESTART IDENTITY CASCADE before each test. Factories build users with an address, products, events and studios with pricing tiers, and studioHour lands on the opening grid past the lead time using the same schedule.ts helpers the service uses. openWriter opens a second raw connection so a test can hold an uncommitted row change while a service call runs, and race(tasks) is Promise.allSettled over 20 racers.

Counts

  • API: 39 unit specs under src, one end to end spec with three tests, and four integration specs with 18 tests.
  • Frontend: 39 unit tests - 26 feature types.test.ts files, nine validation modules, and the stagger, jar surface, format and UI store tests - plus 200 story files that run as tests.
  • The end to end spec boots the whole module with Prisma, Redis and the queue mocked, and asserts the health payload, the request id header and the unauthenticated GraphQL error shape.

Storybook as the component test surface

.storybook/preview.tsx wraps every story in the application's font classes, imports globals.css, and sets a11y: { test: "error" } so an accessibility violation fails the run. Stories are written at four viewports through atViewport, and the storybook vitest project executes them in a real headless Chromium. Containers and providers have no direct tests; their pure reducers do.

Lint and format

  • api/eslint.config.mjs uses recommendedTypeChecked with the project service, plus Prettier as a rule, escalating no-explicit-any, no-floating-promises and no-unsafe-argument to errors. It covers src, scripts, test and prisma/seed.
  • frontend/eslint.config.mjs layers the Next core web vitals and TypeScript configs, the React hooks plugin (which carries the React Compiler rules), and eslint-config-prettier last, ignoring the generated GraphQL output.
  • The root .prettierrc sets double quotes, trailing commas everywhere and LF endings; the frontend adds the Tailwind class-sorting plugin.

Git hooks

  1. commit-msg runs commitlint with the conventional config.
  2. pre-commit runs lint-staged, which formats the frontend, the API and the root files with their respective Prettier installs.
  3. pre-push runs scripts/check-schema-sync.sh, which has three gates: re-emit api/schema.gql and fail if it was stale (it is regenerated in place for you to commit); regenerate the frontend hooks with SCHEMA_URL=../api/schema.gql - pointing at the file so the hook never needs a running server - and fail if they were stale; and run pnpm -C frontend tsc and fail if the frontend no longer typechecks against the schema.

  2. scripts/check-schema-sync.shpnpm -C api schema:emit, then git diff --exit-code on api/schema.gql.

  6. scripts/check-schema-sync.shpnpm -C frontend tsc as the final gate.

Edge cases and failure handling

  • The integration runner does not start Docker. A missing DATABASE_URL or a stopped stack is an immediate, explicit failure.
  • Integration specs run serially with file parallelism off, because they share the sandbox database and truncate between tests.
  • The sandbox is always dropped, in a finally, with FORCE so open connections do not block it.
  • The exit handler prints a message only for non-status errors, so vitest's own exit code propagates without a duplicated stack.
  • Winston is silent under test, so a failing spec's output is the assertion rather than the log.
  • Throttler storage falls back to memory under test, so the specs do not need Redis.
  • The schema sync hook regenerates in place, so a failed push leaves you with the corrected files staged-ready rather than a puzzle.
  • Accessibility violations fail the story run, which is the only automated a11y gate in the repo.

Coverage gaps worth knowing

  • There are no spec files under api/src/queue, api/src/mail or api/src/storage: the queue topology, the retry behaviour, the mail rendering and the S3 client are untested.
  • There is no admin.guard.spec.ts; the admin role check is covered only by two cases inside auth.guard.spec.ts.
  • There are no admin resolver specs and no admin end to end specs.
  • There is no spec for SearchConsumer, EmbeddingsService or reindex-search.ts.
  • There are no tests for gql-throttler.guard.ts, clerk.service.ts, clerk.util.ts or current-user.decorator.ts.
  • On the frontend, containers, providers and the shell and uploads hooks have no tests; the pure reducers they call, and every component through Storybook, do.
  • The legacy import and the seeds have no automated tests.

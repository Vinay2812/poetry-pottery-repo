Testing and verification

Verification has three layers. Unit specs cover the pure logic and the services with their edges mocked. Integration specs run the real services against a real Postgres created and dropped per run, and exist specifically to prove the concurrency guards: twelve files and 61 tests, most of them races with fifteen or twenty simultaneous callers. Storybook runs every presentational component in a real browser with accessibility violations failing the build. Above all three sits a verification skill that drives the real storefront in a browser and keeps screenshots and video as proof, and three git hooks, of which the important one refuses a push whose GraphQL schema and generated hooks have drifted apart.

The integration runner

pnpm -C api test:integration runs api/test/integration/run.ts, which does the following.

  1. loadDotEnv() reads api/.env.
  2. It requires DATABASE_URL with the message DATABASE_URL must point at the compose Postgres. The script starts nothing: the compose stack must already be up.
  3. It generates a sandbox name it_<random hex> and swaps it into the URL path.
  4. It creates that database over a raw pg client. A whole database rather than a second schema, because pgvector is installed per database, so the initial migration's vector(384) columns could not live in another schema.
  5. It runs prisma migrate deploy against the sandbox, so the real migrations are exercised.
  6. It runs vitest with the integration config.
  7. In a finally, it drops the database with WITH (FORCE).

api/test/integration/harness.ts builds a testing module with the real settings, cart, orders, events and workshops services and a real PrismaService wrapped in withAmbientTransactions, stubbing only the outside world: Redis (whose getOrSet calls the loader directly), mail and search. resetData truncates 25 tables in foreign key order with RESTART IDENTITY CASCADE before each test, starting at studio_visits and ending at users. Factories build users with an address, products, events and studios with pricing tiers, and studioHour lands on the opening grid past the lead time using the same schedule.ts helpers the service uses. openWriter opens a second raw connection so a test can hold an uncommitted row change while a service call runs, and race(tasks) is Promise.allSettled over however many racers the spec declares, split into wins and error messages. MailRecorder and QueueRecorder stand in for the two boundaries, so a spec can assert which mails were enqueued and which jobs were published.

Counts

  • API: 75 unit specs under src, one end to end spec with three tests, and twelve integration specs with 61 tests.
  • Frontend: 57 unit test files - 35 feature types.test.ts files, eleven validation modules, and the stagger, vessel, wash, vessels, jar surface, format, browser logger, utils, timezones, site URL and UI store tests - plus 253 story files that run as tests.
  • The end to end spec boots the whole module with Prisma, Redis and the queue mocked, and asserts the health payload, the request id header and the unauthenticated GraphQL error shape.

Storybook as the component test surface

.storybook/preview.tsx wraps every story in the application's font classes, imports globals.css, and sets a11y: { test: "error" } so an accessibility violation fails the run. Stories are written at four viewports through atViewport, and the storybook vitest project executes them in a real headless Chromium. Containers and providers have no direct tests; their pure reducers do. There are no Storybook play functions, so the stories render and are audited but nothing is driven.

The verification skill

.claude/skills/verify-poetry-pottery/SKILL.md is the fourth surface: driving the real storefront the way a shopper does, rather than asserting on a mock. It carries the per-app check commands, the rule never to run pnpm dev to verify, the schema sync fix (pnpm schema:emit then pnpm codegen) and the reminder that a new resolver missing from api/src/resolvers.ts is silently dropped from the schema.

  • Race policy. A race test that fails once in three runs is a finding, not a flake: run it three times when you change one.
  • Launch on non-default ports, API 6066 and frontend 3036, with QUEUE_CONSUMERS_ENABLED=false, waiting on health with until loops rather than sleep, so a verification run never fights a development server.
  • Proof standards. Drive the real path: no eval calling a React setter, no GraphQL request standing in for a click, no test-only route. Verify the side effect rather than the toast. Mock only where production already isolates the outside world, so SMTP, R2 and the queue consumers are boundaries while Postgres, Redis and Clerk are not.
  • Evidence lands under OUT_DIR, by default /tmp/flows: a screenshot per checkpoint plus an automatic one for any failing step, and a 12 fps .webm per flow. Cleanup kills by port, never by process name, and leaves the compose services and the evidence alone, because a cleanup that eats the evidence has failed.

A feature map under features/ holds six files, each to the same four-heading contract of sub-features, how a shopper reaches it, how to drive it, and the gotchas: shop-and-buy.md, saved-pieces.md, open-studio.md, events.md, reach-the-studio.md and account-and-session.md.

browser-flows.sh

frontend/scripts/browser-flows.sh is the harness the skill drives, 611 lines of bash around the agent-browser CLI, taking BASE_URL, API_HEALTH_URL, OUT_DIR and FLOW_SESSION from the environment. Its assertion vocabulary is small and shell-shaped: goto, act, settle, shot, expect_text, expect_no_text, expect_control, expect_url, expect_no_sideways_scroll, click_matching, count_matching.

doctor() runs first and is read only: the agent-browser version, storefront reachability, the API's database, Redis and queue health, whether ffmpeg is present for video, and which session, evidence directory and test user are in play. main refuses to drive an unhealthy stack and exits 2. It then signs in once and dispatches ten flows: home, shop, order, wishlist, events, workshops, contact, newsletter, notfound and signout, reprinting every failure with its flow at the end.

The browser coverage has not caught up with the newest features. There is no flow for studio visits, even though the booking UI renders on /contact beside the contact form that flow_contact does drive; and there is none for commissions, seconds, the glaze pages or the back-in-stock form. Those are covered by the API suite and the unit tests only.

Lint and format

  • api/eslint.config.mjs uses recommendedTypeChecked with the project service, plus Prettier as a rule, escalating no-explicit-any, no-floating-promises and no-unsafe-argument to errors. It covers src, scripts, test and prisma/seed.
  • frontend/eslint.config.mjs layers the Next core web vitals and TypeScript configs, the React hooks plugin (which carries the React Compiler rules), and eslint-config-prettier last, ignoring the generated GraphQL output.
  • The root .prettierrc sets double quotes, trailing commas everywhere and LF endings; the frontend adds the Tailwind class-sorting plugin.

Git hooks

  1. commit-msg runs commitlint with the conventional config.
  2. pre-commit runs lint-staged, which formats the frontend, the API and the root files with their respective Prettier installs.
  3. pre-push runs scripts/check-schema-sync.sh, which has three gates: re-emit api/schema.gql and fail if it was stale (it is regenerated in place for you to commit); regenerate the frontend hooks with SCHEMA_URL=../api/schema.gql - pointing at the file so the hook never needs a running server - and fail if they were stale; and run pnpm -C frontend tsc and fail if the frontend no longer typechecks against the schema.

  2. api/test/integration/run.ts:withAdminCREATE DATABASE over a raw pg client.
  3. api/test/integration/run.ts:runprisma migrate deploy against the sandbox, then vitest with the integration config.
  4. api/test/integration/harness.ts:createHarnessReal services and a real PrismaService wrapped by withAmbientTransactions; Redis, mail and search stubbed.
  5. api/test/integration/harness.ts:resetDataTruncates 19 tables in foreign key order before each test.
  6. api/test/integration/harness.ts:racePromise.allSettled over 20 callers, split into wins and error messages.

  3. api/scripts/emit-schema.tsBuilds the schema from src/resolvers.ts alone, with no database.
  4. scripts/check-schema-sync.shSCHEMA_URL=../api/schema.gql pnpm -C frontend codegen, then a diff on the generated directory.

Edge cases and failure handling

  • The integration runner does not start Docker. A missing DATABASE_URL or a stopped stack is an immediate, explicit failure.
  • Integration specs run serially with file parallelism off, because they share the sandbox database and truncate between tests.
  • The sandbox is always dropped, in a finally, with FORCE so open connections do not block it.
  • The exit handler prints a message only for non-status errors, so vitest's own exit code propagates without a duplicated stack.
  • Winston is silent under test, so a failing spec's output is the assertion rather than the log.
  • Throttler storage falls back to memory under test, so the specs do not need Redis.
  • The schema sync hook regenerates in place, so a failed push leaves you with the corrected files staged-ready rather than a puzzle.
  • Accessibility violations fail the story run, which is the only automated a11y gate in the repo.

Coverage gaps worth knowing

  • There are no spec files under api/src/queue, api/src/mail or api/src/storage: the queue topology, the retry behaviour, the mail rendering and the S3 client are untested.
  • There is no admin.guard.spec.ts; the admin role check is covered only by two cases inside auth.guard.spec.ts.
  • There are no admin resolver specs, although admin-guards.spec.ts asserts the guard on every field of all fourteen admin resolvers, and admin.integration-spec.ts covers the console under contention.
  • There is no spec for SearchConsumer, StorageConsumer, MailConsumer, EmbeddingsService or reindex-search.ts; NotificationsConsumer is the one consumer that has one.
  • There is no integration spec for commissions, and no direct template test for backInStockMail, orderStudioNoteMail or either commission mail.
  • StorageResolver.createCustomizationUpload has no spec, so its narrower MIME allowlist and its guard stack are untested.
  • There are no tests for clerk.service.ts, clerk.util.ts or current-user.decorator.ts; gql-throttler.guard.spec.ts now exists.
  • On the frontend, containers, providers and the shell and uploads hooks have no tests; the pure reducers they call, and every component through Storybook, do.
  • The legacy import and the seeds have no automated tests.

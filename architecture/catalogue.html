Catalogue and search

One resolver and one service back the shelf, the dated archive wall and the search page. Availability is expressed as a composable Prisma predicate and the archive is defined as its exact negation, so nothing can fall between the two tabs. A search term first narrows the candidate set through a hybrid Postgres query that ranks a weighted tsvector match alongside pgvector cosine similarity, with the embedding computed locally in the API process; facets, both tab counts and the page then come back in one round trip. A separate, much smaller query backs the header typeahead, and a piece now carries measured facts, a named glaze and, when the kiln left a mark on it, the flaw that made it a second.

Architecture

How it works

Availability is a predicate, and the archive is its negation

The shelf and the archive are one query with one scope swapped. The spec asserts the relationship literally: archivedProductWhere(NOW) deep-equals { NOT: availableProductWhere(NOW) }, so a piece can never fall through both tabs or appear on both.

Availability and archive predicates from api/src/features/products/products.service.ts.
HelperPredicate

The cart's add path uses sellableProductWhere, not availableProductWhere, because stock is checked separately and a made-to-order piece with zero stock must still be addable.

The list query

  1. clampPage(filter.page, filter.limit, MAX_LIMIT = 48) produces { page, limit, skip }.
  2. A non-empty search term goes to SearchService.rankProducts(term, SEARCH_CANDIDATES = 200), returning product ids in rank order. Guard: an empty ranked set short-circuits to an empty page with empty facets, skipping every database query.
  3. scope is the archive or availability predicate. pool holds the filters that must not become facets: the ranked id set, and customizable_only.
  4. narrowing holds one where-clause per key in NARROW_KEYS = ["category", "collection", "material", "glaze", "price", "stock", "seconds"]. Glaze is { glaze: { slug: { in: filter.glaze_slugs } } } and seconds is { is_second: true }; both are narrowing rather than pool filters, so they apply to the shelf and the archive alike.
  5. Four queries run in parallel: the rows, the facets, the active tab count and the archive tab count. The two counts use the same narrowing, so the inactive tab's number is always accurate in the same round trip.
  6. In the search branch there is no orderBy, skip or take. Rows are ordered by sortByRank and then sliced in memory, because relevance order cannot be expressed in the Prisma ordering.

Facets

  • Self exclusion. A facet's counts respect every other active narrowing filter but never its own, via scoped("category"), scoped("collection"), scoped("material"), scoped("glaze") and scoped("seconds"), so choosing an option never makes its siblings vanish. Price and stock are not option lists and are not self excluded.
  • The option lists are the whole catalogue, zero counts included, so the sidebar never reflows.
  • Five parallel queries: categories with a filtered _count, collections with a filtered _count, the material names (global groupBy, no where), the material counts (filtered groupBy), and a global price aggregate. The price slider bounds therefore stay catalogue wide even for a one-result search.
  • Seven parallel queries now, because the glaze facet and the seconds count joined the five. The glaze facet is a glaze.findMany with a filtered relation _count rather than a groupBy, so a glaze nothing currently matches still appears with a zero. seconds_count is a plain count under scoped("seconds"), that is, under every other filter but not the toggle itself.

The Glaze model

A glaze is a material the studio names, not a colour word: it behaves a certain way in the kiln and it varies, and the schema says both out loud. Glaze carries slug @unique, name, a required description, an optional variation_note, an optional swatch_url and an optional color_code. Product.glaze_id is nullable with onDelete: SetNull and its own index, so a piece may wear no glaze and deleting a glaze can never orphan a row.

  • Two public queries: glazes ordered by name, and glaze(slug). A separate GlazeResolver adds Glaze.pieces, which is { ...availableProductWhere(), glaze_id } in the featured sort, so a glaze page is shelf only and never shows the archive.
  • The console module is api/src/features/admin/glazes. Slugs come from the name through slugify and uniqueSlug and are never client supplied; parseColorCode keeps a six-digit hex and refuses anything else with A glaze colour must be a hex like #6F7D6B; the swatch goes through assertConfirmed(..., UploadPurpose.GLAZE); and every write calls invalidateCatalogCache().
  • Deleting a glaze pieces still wear is refused, with N pieces still wear this glaze; move them first, because SetNull would quietly strip the glaze off every one of them.
  • On the storefront the glaze appears as GlazeNote under the buy box: swatch, description, variation note and a "See everything in this glaze" link to /products?glaze=<slug>.

Piece facts

There is no facts model. Five nullable columns sit on Product under one comment: what the piece is in the hand, filled in per piece, never guessed. They are capacity_ml Int?, height_cm and diameter_cm as Decimal(5,1), weight_g Int? and maker_note String?, added by the 20260917100000_piece_facts migration together with the glazes table. There is no firing or clay body column; "clay body" is the label the kiln card puts on material.

  • Prisma Decimal does not cross GraphQL, so toProduct(row) runs the two centimetre columns through toCm and the schema exposes them as Float. Every read path, list, bySlug, related, featured and glazePieces, goes through toProduct.
  • The ProductCard fragment deliberately does not select them, so a grid never pays for facts it will not show.
  • toFactRows in frontend/src/features/products/types.ts builds the kiln card in a fixed order, dropping any row whose value is null: clay body, glaze (or Chosen with you for a made-to-order piece), size, capacity, weight, then two hard-coded lines, Made in Sangli, Maharashtra and a ships-in line. toSizeLine prefers the studio's written dimensions and only falls back to the measurements.
  • Admin writes go through assertMeasure, whose rule is that a measurement is either a positive number or missing and zero is never a real piece. Caps are 20,000 ml, 999 cm each way and 50,000 g. The form section is headed "Size and weight" with the hint to leave a box empty until the piece has actually been measured, and the console shows "Not measured yet" rather than inventing a zero.

The scale drawing. PieceScale draws the piece beside a standard 250 ml cup at true relative scale. toPieceScale works in tenths of a centimetre (SCALE_UNITS_PER_CM = 10) so no path number is rounded past a millimetre, places both silhouettes on one floor at y = 0, and sizes the viewBox from the taller of the two. The reference is REFERENCE_CUP, 9 cm tall and 8 cm across; a piece with no recorded diameter borrows the cup's width-to-height ratio. It shares the drawing engine: toSilhouette in components/media/vessels.ts reuses the same profile specs and the same wallSpline and closedBody from lib/drawing/vessel.ts that the hero jar and every placeholder use, so a drawn scale and a drawn placeholder come out of the same hand. See the design page.

The maker's note is one <p>, MakerNote, set in the script face that is reserved for it and nothing else, rendered between the kiln card and the glaze note. The API trims it to null on write.

The seconds shelf

is_second Boolean @default(false) and flaw_note String? travel together, because a second is only honest if the flaw is named. assertSecond(isSecond, flawNote) refuses a second with a blank note (Say what the kiln left on this piece), and update validates the merged pair against the stored row, so flipping the flag alone keeps the note that is already there. The zod schema mirrors the rule, and the console only shows the flaw-note field once the box is ticked.

  • There is no /seconds route. It is a URL toggle on the shelf, seconds=1, rendered as a switch labelled with its own count and helped by the line about pieces the kiln marked, sold at a lower price with the flaw named. Because it narrows rather than pools, it works on the archive tab too.
  • Nothing discounts a second automatically. is_second never touches price anywhere in the code; the studio sets price below compare_at_price by hand and PriceTag strikes the old one through.
  • On a card, toCardStatusLine joins Second with the stock line, so a marked piece with two left reads Second · Only 2. On the product page SecondNotice is headed "What is different about this one" and toFlawNote falls back to a general line when the note is blank.

The block is words only. Product has one image_urls array and no flaw shot in it, so SecondNotice used to be handed flawPhotoUrl={product.image_urls[0] ?? null} and presented the gallery's lead photograph as the mark — a picture of the piece at its best, captioned as the thing wrong with it. The photo is gone: the component now takes a single flawNote prop and renders a heading and a paragraph. Its own comment records the condition for bringing an image back, which is the catalogue carrying a real flaw shot rather than borrowing one. docs/design/ui-audit.md has the original finding.

The archive wall

/archive is a server component with no client bundle of its own. It calls getArchiveWall(48), which is the ordinary products(filter:) query with archive: true and the newest sort, over a lean ArchivePiece fragment. There is no bespoke archive API.

  • toArchiveYears groups the result newest year first, then by collection in first-appearance order, with anything uncollected landing under Odd pieces. Dates are read in Asia/Kolkata, and each tile carries toMadeLabel, for example Made March 2026.
  • An ArchiveTile is bigger than a shelf card and carries no price: the photograph is the point. A startIndex per shelf feeds toCardPhotoLoading, so only the first tiles load eagerly.
  • Provenance is toProvenance(createdAt, glaze, clayBody, stock), one line saying where a piece came from and where it went: the made label, the glaze, the clay body, and then either has found a home when stock is zero or no longer on the shelf when it was merely retired. The wall itself does not render it; it appears on the product page, inside ArchiveNotice, where it replaces the buy box along with an "Ask for one like it" WhatsApp link. The glaze argument passed there is product.color_name, not product.glaze?.name.
  • The shelf keeps its own in-page archive tab, but ProductListContainer sets that tab's href to /archive and intercepts only the shelf tab, so the archive tab is a real link to the gallery rather than a filter flip.

Typeahead

suggest(q) is a public, unguarded query in api/src/features/suggest, deliberately three short lists rather than a page of results: MAX_PIECES = 4, MAX_EVENTS = 3, MAX_WORKSHOPS = 2.

  1. normaliseTerm trims, collapses runs of whitespace and cuts at MAX_TERM_LENGTH = 80. Below MIN_TERM_LENGTH = 2 it returns a shared empty object without touching Redis or Postgres at all.
  2. Everything else is redis.getOrSet("suggest:<lowercased term>", SUGGEST_CACHE_SECONDS = 30, loader). Thirty seconds is short enough that a new piece shows up almost at once and long enough to absorb a burst of typing. Like every cache here, a Redis outage degrades to the loader.
  3. Pieces and events reuse rankProducts and rankEvents, then a findMany on the ranked ids, re-ordered by inRankOrder because findMany loses rank order. Pieces carry no availability scope: an archived piece is suggested and labelled In the archive rather than hidden. Events are narrowed to PUBLISHED.
  4. Wheel sessions are not indexed at all, there being a handful of them, so workshops are a plain case-insensitive contains on the name.

It carries no @StrictThrottle(), so it sits under the global default and short profiles only. On the client the term goes through useDeferredValue rather than a timer, gated at the same length of two, and previousData keeps the rows up so the list never blinks empty. The panel itself is described on the shell page.

Sorting

Every entry in SORT_ORDER ends with an id tiebreaker, which is what keeps pages from skipping or duplicating a row: featured is is_featured, sales_count, id; newest is created_at, id; best selling is sales_count, id; the two price sorts are price, id; top rated is rating_avg, rating_count, id. Sort is ignored entirely when a search term is present, because relevance wins.

Hybrid search

Postgres keeps a weighted tsvector per product and per event, maintained by a BEFORE INSERT OR UPDATE trigger created in the initial migration, so application code never writes it and it can never drift from the row. For products the weights are A for name, B for material and color_name, C for description; for events A is title, B is location and instructor, C is description. Both tables carry a GIN index on the column.

A vector(384) column holds the embedding. There is deliberately no ANN index; the migration says the catalogue is small enough that an exact scan is fast and precise. The ranking query in search.service.ts:rankQuery keeps every keyword hit and adds semantic hits whose cosine distance is under MAX_SEMANTIC_DISTANCE = 0.55:

  • Predicate: search_vector @@ websearch_to_tsquery('english', term) or embedding IS NOT NULL AND (embedding <=> vector) < 0.55.
  • Order: ts_rank(search_vector, websearch_to_tsquery('english', term)) * 2 + COALESCE(1 - (embedding <=> vector), 0) DESC, id DESC. Keyword rank is weighted twice, semantic similarity is 1 - distance, a null embedding contributes zero rather than nulling the sum, and id is the deterministic tiebreaker.
  • Scope: products carry no availability filter inside the ranking, so the same ranking serves the shelf and the archive. Events exclude only status = 'DRAFT', so completed events stay searchable.

Embeddings

There is no hosted embedding provider and no API key. EmbeddingsService runs @huggingface/transformers in the API process: a lazily created singleton promise builds a feature-extraction pipeline for env.EMBEDDINGS_MODEL (default Xenova/all-MiniLM-L6-v2) with dtype: "q8", caching the model under env.EMBEDDINGS_CACHE_DIR (default .cache/models). embed(text) trims to 2000 characters and runs with pooling: "mean" and normalize: true, which is what makes 1 - distance a meaningful similarity.

On the query side SearchService.safeEmbed catches any failure, logs a warning and returns null, which drops rankQuery to the keyword-only branch. On the index side indexProduct and indexEvent call embed without that guard, so a failure throws, the consumer NACKs, and the job dead-letters.

Indexing and reindex

Admin writes call afterWrite(productId), which invalidates the catalogue cache and then search.requestProductIndex(id); the events equivalent calls requestEventIndex. That publishes search.index-product or search.index-event on the poetry exchange. SearchConsumer validates the payload with the shared zod schema and calls back into SearchService, which builds the text, embeds it and writes the vector with a raw UPDATE ... SET embedding = $1::vector. The product embedding text includes category names, which the tsvector does not.

pnpm search:reindex runs api/scripts/reindex-search.ts, which boots a Nest application context with QUEUE_CONSUMERS_ENABLED=false so the one-shot script cannot drain the live queues, then calls SearchService.reindexAll(). That walks products and then events in two sequential loops, deliberately serial so one transformers pipeline is not hammered concurrently, and reports the counts attempted.

Caching

categories() and collections(archive) sit behind redis.getOrSet with CATALOG_CACHE_SECONDS = 120 under the keys catalog:categories, catalog:collections and catalog:collections:archive. Collections with zero matching products are filtered out so an empty strip never renders. invalidateCatalogCache() deletes all three and is called from the admin products and admin catalog services.

URL-driven filters on the client

frontend/src/features/products/types.ts:parseFilters reads q, category, material, collection, min, max, in_stock=1, customizable=true, view=archive and sort, accepting both repeated parameters and comma lists, clamping integers and falling back to ProductSort.Featured on junk. toSearchParams is the inverse and omits every default, so the canonical shelf URL is bare.

ProductListContainer holds useOptimistic(urlFilters, applyFilterAction) plus useTransition, with a pendingRef so back to back clicks stack on each other instead of each rebasing on the not yet committed URL. Navigation is router.replace(..., { scroll: false }), so filtering does not pollute history. Search is debounced at 300 ms, the field prefers its local draft until the URL catches up, and useDeferredValue lets the input paint per keystroke while results follow at lower priority.

Edge cases and failure handling

  • Deep search pages disagree with the total. SEARCH_CANDIDATES = 200 caps the ranked set, so a very broad term returns nothing past skip >= 200 while page_info.total still reports the true count.
  • The price slider is catalogue wide. The min and max aggregate ignores every filter and both scopes, so a one-result search still shows the full range. Selecting the full range removes the parameters rather than pinning the bounds.
  • Cache invalidation is delete after write with no versioning. A concurrent getOrSet that already read the old row can write it back just after the delete, serving stale data for up to the 120 second TTL.
  • Redis being down is not an error. getOrSet swallows both the read and the write failure and falls through to the loader.
  • A deleted product between enqueue and consume is handled: indexProduct returns silently when the row is gone.
  • Out of order reindexing. With prefetchCount: 4 and one queue per job type, two rapid edits to the same product can be processed concurrently and the last write wins arbitrarily. There is no per-product lock or version check; the impact is a stale but valid vector that heals on the next edit or reindex.
  • A failed model load poisons the process. this.extractor ??= caches the promise, including a rejected one, so a single failed load disables embeddings for the lifetime of the process.
  • A GraphQL error with cached previousData keeps stale results on screen; LoadFailed only renders when there is an error and no result at all.
  • Archived pieces are viewable. bySlug applies no availability predicate, so an archived product still has a page; it is the buy box that is replaced by the archive notice.
  • A glaze cannot be deleted out from under its pieces, because the service refuses while any wear it, even though the foreign key would have set them null.
  • The seconds toggle survives a tab switch, since it narrows rather than pools; the customisable filter and the search term do not.
  • A piece with no recorded diameter still draws to scale, borrowing the reference cup's ratio, and a piece with no recorded height draws nothing at all.
  • The typeahead suggests archived pieces on purpose, labelled rather than filtered, so a search for something that has sold leads to its page.
  • The suggest cache is not invalidated by an admin write; only its 30 second TTL clears it.

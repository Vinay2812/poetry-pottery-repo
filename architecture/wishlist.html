Wishlist

The wishlist is the smallest feature in the system and the clearest example of the house pattern: a cheap id-only query feeds every heart on the site, one idempotent toggle mutation flips membership inside a transaction, and the browser holds an optimistic id set that it settles from two awaited refetches because the mutation deliberately answers with a count rather than a list.

Architecture

How it works

Three operations, one of them cheap on purpose

  • wishlist returns the full cards, including the product with its list include.
  • wishlistIds returns just the product ids. This is the query every heart on the site reads, so that a grid of cards costs one small array rather than a page of products.
  • toggleWishlist(product_id) returns WishlistToggleResult { product_id, is_wishlisted, wishlist_count }.

All three are @AuthRequired(). WishlistService.remove exists but no resolver exposes it; the toggle covers both directions.

Saved pieces are not filtered

list deliberately does not apply sellableProductWhere, so an archived piece stays on the list; the card simply stops offering the cart. toggle likewise looks the product up without the sellable predicate, so an archived piece can still be saved and unsaved.

The toggle

Inside a transaction, toggle first runs wishlistItem.deleteMany({ user_id, product_id }). A non-zero count means it was on and is now off, and the function returns false. Otherwise it runs createMany({ data, skipDuplicates: true }) and returns true. skipDuplicates together with the @@unique([user_id, product_id]) constraint is the double-tap guard: a racing insert is swallowed rather than raising P2002. The count is read after the transaction.

Product.in_wishlist

The field resolver on Product memoises a promise on the request object: req.wishlistIds ??= authGuard.tryAuthenticate(req).then(...). One optional authentication and at most one wishlist query serve a whole page of products, and an anonymous visitor resolves to an empty set.

The optimistic layer

WishlistProvider holds useOptimistic(ids, applyWishlistToggle) and useTransition, exposing the pending flag as isSaving. The next state is computed from the optimistic list, not from the server list, so rapid double taps alternate correctly. Because the reply carries only a count, the provider settles with refetchQueries: ["WishlistIds", "Wishlist"] and awaitRefetchQueries: true; both refetched lists are the new baseline.

useWishlist runs the full Wishlist query for the cards but filters it by the optimistic id list, so un-hearting drops the card immediately while the Wishlist refetch is still in flight. applyWishlistToggle appends when absent (keeping order), filters on removal, never duplicates and always returns a new array.

Minimal theory: call trace

  1. frontend/src/features/products/containers/ProductCardContainer.tsxHeart click calls the provider's toggle(productId, productName).
  2. frontend/src/features/wishlist/containers/WishlistProvider.tsx:togglerequireAuth first; computes isWishlisted = !optimisticIds.includes(productId) from the optimistic list.
  3. frontend/src/features/wishlist/types.ts:applyWishlistTogglePure reducer: append or filter, always a new array.
  4. api/src/features/wishlist/wishlist.resolver.ts:WishlistResolver.toggleWishlist@AuthRequired(); the product id is the only input.
  5. api/src/features/wishlist/wishlist.service.ts:WishlistService.toggleProduct existence check, then inside a transaction deleteMany and, when nothing was deleted, createMany with skipDuplicates.
  6. api/src/features/wishlist/wishlist.service.ts:WishlistService.toggleAfter the transaction, counts the user's rows for the badge.
  7. frontend/src/features/wishlist/containers/WishlistProvider.tsxAwaits the WishlistIds and Wishlist refetches, which become the baseline; failure toasts and the optimistic id snaps back.

Edge cases and failure handling

  • Double tap. The unique constraint plus skipDuplicates absorbs a racing insert. Two interleaved toggles can settle in either state, which is accepted: the awaited refetch decides.
  • Unknown product raises NotFoundException("Product not found").
  • Archived pieces stay saved, which is deliberate; the card hides the cart button instead.
  • Signed-out visitors never fire the query (skip: !isSignedIn) and the heart routes through useRequireAuth into the sign-in prompt.
  • A failed toggle surfaces as toast.error(message ?? "Could not update your wishlist") and the optimistic id reverts when the transition ends.
  • WishlistService.remove is unreferenced dead surface in the service.

Tests

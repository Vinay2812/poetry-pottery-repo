Legacy import and seeding

The catalogue on this site is not seeded data, it is the old production database, imported by a script that opens the source read only and writes everything through upserts on natural keys so it can be run again whenever the schema moves. The seeds cover only the scaffolding the import does not carry: the studio configuration, the site settings singleton and the public content pages, with a separate optional demo catalogue for local play.

Architecture

How it works

Connecting

api/scripts/import-legacy.ts reads LEGACY_DATABASE_URL at module scope, straight off process.env rather than through the zod schema, and throws LEGACY_DATABASE_URL is not set when it is missing. The legacy pg client runs set default_transaction_read_only = on immediately after connecting, so the source cannot be written to even by accident. The destination is a fresh Prisma client on env.DATABASE_URL.

A module-level types.setTypeParser(types.builtins.TIMESTAMP, v => new Date(${v}Z)) is needed because the legacy timestamp without time zone columns hold naive UTC and must not be read as local wall time. json_agg output bypasses that parser, so the workshop slot strings are re-suffixed with Z by hand.

Reading

readLegacy() issues ten queries, all ordered by id or creation time: users; user addresses; collections; products joined to their categories with an aggregated name array; customise categories left-joined to their options, filtered to active ones; the daily workshop configs and pricing tiers (where c.is_active and limit 1, so only one config is imported); workshop registrations with their booked slots aggregated; cart lines; the active about content page; and two site settings rows, contact_info and hero_images.

Writing, in order

main runs importUsers, importCatalog, importCustomPieces, importWorkshop, importCart and importContent. The id maps returned by the first two feed the later steps.

Every write is an upsert on a natural key, which is what makes the import idempotent.

Two things are recreated rather than upserted: a product's option groups are deleted and rebuilt, and a config's pricing tiers are deleted and re-created. Addresses have no stable cross-schema key, so importUsers looks for a matching (user_id, line1, pincode) and updates it when found, so an identical line is never duplicated.

Mapping decisions worth knowing

  • Product slugs come from the name, not the legacy slug, because the legacy slugs were junk. A collision appends the legacy id, tracked in a used-slug set.
  • toColorCode keeps only a value matching /^#[0-9a-f]{6}$/i, because the legacy form stored palette indexes in the hex field.
  • toDescription keeps text longer than three characters and otherwise substitutes a studio fallback line.
  • Stock is Math.max(available_quantity, 0) and material defaults to Stoneware; created_at is preserved throughout.
  • A user's subscribed_to_newsletter flag becomes a newsletterSubscriber row, dated from the legacy subscription timestamp, and an update re-activates it.
  • Addresses map zip to pincode, with the contact number falling back to the owning user's phone.
  • Each customise category becomes one made-to-order product slugged custom-<singular>, with stock zero, is_customizable true, a required CHOICE group named Size when options exist, and always an optional TEXT group "Notes for the potter" capped at 200 characters.
  • The workshop import converts hours to minutes and maps the slot duration, capacity and booking window. On update it deliberately passes name: undefined and description: undefined, so the seeded config keeps its own copy and image and only the real hours and prices come across. Legacy bookings stored one row per booked hour, and those become the booking's slot rows, with starts_at from the first and ends_at from the last; a legacy PAID status maps to CONFIRMED.
  • importContent builds up to three sections for the about page - the story, "What we believe" from the values list and "How a piece is made" from the process steps - and writes the contact details into site settings, deriving the WhatsApp number by stripping non-digits from the phone.

What is skipped

Addresses, bookings and cart lines without a resolvable user are skipped; bookings with no slots are skipped; only the first active workshop config is read; inactive customisation options are filtered out in SQL; non-hex colour codes are dropped. Legacy events, orders, reviews and wishlists are never read at all - the documentation records them as zero rows. --dry-run prints the counts and returns before any write.

Seeds

  • pnpm db:seed runs api/prisma/seed/index.ts, which is site scaffolding only: the workshop config with its tiers, the site settings singleton and the six public content pages. Its header comment says the catalogue comes from the legacy import.
  • api/prisma/seed/content.ts holds seven events, the open-studio config and tiers, the site settings and the content pages, plus coupons.
  • api/prisma/seed/catalog.ts holds seven categories, the collections, the products, the care notes and the custom mug options. Its photographs are Pexels stock, scoped to the demo seed by docs/design/temporary-photos.md.
  • pnpm db:seed:demo runs demo.ts, an optional local catalogue that seeds products, events with starts_at computed from a day offset at 15:00 IST and available_seats derived from the booked count, and coupons.

The other scripts

  • pnpm make-admin <email> finds exactly one Clerk user for the address, upserts the database row with the admin role and writes dbUserId and role back into Clerk's public metadata. The upsert is needed because signing in alone does not create the row until the first authenticated API call.
  • pnpm search:reindex boots an application context with consumers disabled and calls SearchService.reindexAll().
  • pnpm schema:emit boots only the GraphQL schema builder over src/resolvers.ts and writes api/schema.gql with a banner byte-identical to what autoSchemaFile writes at boot, so the two writers never diff. It needs no database.
  • api/prisma.config.ts calls loadDotEnv() first, because Prisma 7 no longer loads .env itself.
  • pnpm db:reset:legacy chains reset, import and reindex.

Minimal theory: call trace

  1. api/scripts/import-legacy.tsModule scope: reads LEGACY_DATABASE_URL and installs the UTC timestamp parser.
  2. api/scripts/import-legacy.ts:mainThrows when the URL is missing; connects and sets the session read only.
  3. api/scripts/import-legacy.ts:readLegacyTen ordered queries into one in-memory snapshot.
  4. api/scripts/import-legacy.ts:importUsersUpserts users on auth_id, creates newsletter rows, and matches addresses on line and pincode.
  5. api/scripts/import-legacy.ts:importCatalogCategories, collections and products, slugging from the name with an id suffix on collision.
  6. api/scripts/import-legacy.ts:importCustomPiecesOne made-to-order product per customise category, with a Size choice group and a notes text group.
  7. api/scripts/import-legacy.ts:importWorkshopConverts hours to minutes, rebuilds tiers, and turns each legacy booked hour into a slot row.
  8. api/scripts/import-legacy.ts:importCartUpserts cart lines with an empty selection key.
  9. api/scripts/import-legacy.ts:importContentBuilds the about page sections and the contact settings.
  10. api/scripts/reindex-search.tsRun afterwards, as the script's own closing line instructs, to embed the imported rows.

Edge cases and failure handling

  • The source is read only by construction, set on the session rather than trusted from a role.
  • Naive UTC timestamps would otherwise shift by the local offset; the type parser and the manual Z suffix on aggregated JSON handle both paths.
  • Re-running is safe. Every write is keyed on something natural, so the import converges rather than duplicating.
  • Option groups and pricing tiers are rebuilt, so a removed option disappears rather than lingering.
  • Only one workshop config is imported, by an explicit limit 1.
  • Rows without a resolvable owner are skipped silently, which is why the printed counts are the reliable summary.
  • Embeddings are not written by the import; it tells you to run the reindex, and db:reset:legacy chains it for you.
  • Failures print a stack and set a non-zero exit code, and the Prisma client is always disconnected in a finally.

Tests

  • There are no automated tests for the import or the seeds. The verification path is --dry-run plus the row counts recorded in docs/data/legacy-import.md, which documents what the real production database contained: 21 products of which 13 are active, six categories, six collections, three customise categories, eight users of whom five are admins, three addresses, one cart line, one workshop config with five tiers, two pending bookings, the about page and the contact settings, and zero events, orders, reviews and wishlists.
  • That document also records the design consequences of the real data: tiny stock counts, poem-style descriptions, non-hex colour codes, "Wood Fired" being a process rather than a form, a price span from ₹300 to ₹25,000, and the ten and thirteen hour courses being rendered as multi-day WhatsApp requests.
  • api/eslint.config.mjs does lint prisma/seed/** and scripts/** under the type-checked rule set, so the scripts are at least held to the same typing standard as the application.
  • The import predates the glaze table, the piece facts and the seconds fields, so it leaves every one of them null or false. An imported piece has a material and a color_name but no glaze_id, no measurements and no maker's note until somebody fills them in from the console.

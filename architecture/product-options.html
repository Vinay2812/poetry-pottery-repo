Product page and made-to-order options

A made-to-order piece carries option groups: either a set of choices or a length-capped free-text field, each with its own price modifier. The browser prices and validates a customisation so the buy button can show an honest total, and then the server ignores all of that and re-derives the price from the live option rows. The result is hashed into a stable selection key, which is what decides whether two additions of the same product merge into one cart line or sit side by side as two.

Architecture

How it works

The models

ProductOptionGroup holds name, kind (CHOICE or TEXT), is_required, price_modifier, max_length and sort_order. A TEXT group prices the free-text entry itself and caps its length; a CHOICE group owns ProductOption rows, each with its own price_modifier, sort_order and is_active. Both cascade from the product.

CartItem carries selections Json? typed as PrismaJson.ProductSelection[] (group_id, group_name, option_id, option_name, text, price_modifier) and a selection_key String @default(""), with @@unique([user_id, product_id, selection_key]).

Server-side resolution

api/src/features/cart/selections.ts:resolveSelections(groups, inputs) iterates the live option group rows in server order, never the client's array, and builds priced snapshots.

  • TEXT: trim the input. Empty and required raises <group> is required; empty and optional is skipped entirely and contributes no price. Longer than max_length raises <group> must be N characters or fewer. The stored price_modifier is the group's.
  • CHOICE: a missing option_id on a required group raises Choose a <group>; on an optional group it is skipped. The option is looked up with c.id === optionId && c.is_active, so an unknown id and a deactivated option produce the same That <group> is no longer available. The stored price_modifier is the option's.
  • After the loop, any input naming a group that does not belong to this product raises Unknown customisation option, which blocks cross-product option injection.
  • A product that is not is_customizable silently drops any selections the client sent.

The selection key

selectionKey(selections) returns "" for an empty selection set, which is the column default, so uncustomised lines merge under the same unique constraint. Otherwise it copies the array, sorts by group_id, maps each entry to the triple [group_id, option_id, text], JSON.stringifys that canonical form, takes a SHA-256 and keeps the first 32 hex characters (128 bits).

  • Sorting by group_id makes the key order independent, so the same choices submitted in any order merge into one cart line.
  • price_modifier, group_name and option_name are deliberately outside the key, so renaming a group or repricing an option does not fork an existing line.
  • The copy before sorting means the caller's array is never mutated.

Add to cart

CartService.add truncates the quantity and refuses anything outside 1 to MAX_LINE_QUANTITY = 10, then loads the product with sellableProductWhere() and all of its options, including inactive ones, so resolveSelections can reject them with the right message. It resolves the selections, computes the key, and then inside a transaction takes pg_advisory_xact_lock(userId, productId), reads the existing line, merges with Math.min(MAX_LINE_QUANTITY, existing + incoming), asserts stock for non-customisable pieces, and upserts. The update branch writes only the quantity, so an existing line's stored selection snapshot and its prices are never rewritten.

Pricing on read

toCartItem computes unit_price = product.price + selectionsTotal(row.selections) and line_total = unit_price * quantity. The selection price modifiers are a snapshot frozen at add time, while the base product.price is read live, so an admin price change moves the base but not the option deltas.

The client half

ProductDetailContainer keeps a selections record where each group holds exactly one value, so picking an option clears any text for that group and vice versa. computeUnitPrice and validateSelections in frontend/src/features/products/types.ts mirror the server rules, but only advisorily; errors are rendered only after a submit attempt (showErrors). OptionGroupPicker is pure: the TEXT branch sets a hard maxLength on the input with a live counter and aria-invalid, and the CHOICE branch renders a fieldset and legend with aria-pressed buttons. The GraphQL document does not select is_active, because the storefront resolver already filters to active options.

The sticky buy bar is driven by an IntersectionObserver on the buy box, cleaned up on unmount. product.is_archived is computed on the server and swaps the buy box for ArchiveNotice.

Reference photos for made-to-order pieces are not implemented. There is no reference image field on option groups, options or cart items, OptionGroupKind has only CHOICE and TEXT, and customer imagery has no upload path. The only escape hatch is the WhatsApp ask link built by toGlazeAskUrl and toArchiveAskUrl. Image uploads exist on the admin side only.

Minimal theory: call trace

Rendering the product page

  1. frontend/src/app/(storefront)/products/[slug]/page.tsx:ProductPageAwaits params, then Promise.all([getProduct(slug), getSiteSettings()]), and calls notFound() on a null product.
  2. frontend/src/lib/data/catalog.ts:getProductServer query with errorPolicy: "all". Only a real 404 becomes null; any other failure rethrows and surfaces as an error page.
  3. api/src/features/products/products.resolver.ts:ProductsResolver.productbySlug with no availability predicate, so archived pieces still have a page.
  4. api/src/features/products/products.resolver.ts:ProductsResolver.option_groupsField resolver; the list and detail queries never preload the groups, so this always calls the service.
  5. api/src/features/products/products.service.ts:ProductsService.optionGroupsOrders groups and options by sort_order and filters options to is_active: true.
  6. frontend/src/features/products/containers/ProductDetailContainer.tsx:ProductDetailContainerHolds selections, memoises computeUnitPrice and validateSelections.

Adding a customised piece

  1. frontend/src/features/products/containers/ProductDetailContainer.tsx:handleAddToCartGuards on client validation issues, then flattens the selections record into { group_id, option_id, text } entries.
  2. frontend/src/features/cart/containers/CartProvider.tsx:addToCartWrapped in useRequireAuth; deliberately not optimistic, because stock is the server's call.
  3. api/src/features/cart/cart.resolver.ts:CartResolver.addToCart@AuthRequired(); the user id comes from @CurrentUser(), never from the input.
  4. api/src/features/cart/cart.service.ts:CartService.addTruncates and range-checks the quantity, then loads the product with sellableProductWhere() and all option rows.
  5. api/src/features/cart/selections.ts:resolveSelectionsRe-prices every selection from the live rows and rejects missing, overlong, unknown or deactivated ones.
  6. api/src/features/cart/selections.ts:selectionKeyCanonicalises and hashes the selections to decide which line this belongs to.
  7. api/src/prisma/prisma.service.ts:PrismaService.withTransactionOpens (or joins) the transaction the advisory lock lives in.
  8. api/src/features/cart/cart.service.ts:CartService.addpg_advisory_xact_lock(userId, productId), read the line, merge and clamp, assertStock, upsert on the compound unique.
  9. api/src/features/cart/cart.service.ts:CartService.getEvery mutation returns the whole recomputed cart, so the client never patches one by hand.

Edge cases and failure handling

  • A merge that would exceed ten saturates rather than erroring. Math.min(MAX_LINE_QUANTITY, ...) is silent by design.
  • An option deactivated between page load and add surfaces as the server's That <group> is no longer available; the client cannot see it coming because the storefront query never selects is_active.
  • Overlong text is mostly unreachable through the UI, because the input carries a hard maxLength, but the server rule still exists for direct API callers.
  • Price drift. Selection modifiers are snapshotted on the cart row while the base price is live, so a repricing changes part of the line total and not the rest.
  • Archived and closed-collection pieces cannot be added at all, because add filters with sellableProductWhere() and a miss is NotFoundException("Product not found").
  • Two tabs adding the same piece are serialised by the advisory lock, which is keyed on (user, product) rather than on the selection key, so different customisations of the same product also queue up. That is coarser than strictly necessary and never deadlocks with itself.

Tests

  • api/src/features/cart/selections.spec.ts covers pricing from live rows, optional text being skipped, the required, inactive, overlong and unknown rejections, and that the key is order independent, 32 characters long and empty for an empty selection set.
  • api/src/features/cart/cart.service.spec.ts covers merging into an existing line and capping at the stock, and holding back a line whose collection window has not opened or has closed.
  • api/test/integration/cart.integration-spec.ts proves the advisory lock under 20 concurrent adds.
  • frontend/src/features/products/types.test.ts covers the customisation pricing helpers and the missing and overlong reports.

Poetry and Pottery architecture

Overview and repo layout

Poetry and Pottery is an e-commerce platform for handcrafted pottery with workshop and event booking, built as three independent applications in one repository: a Next.js storefront and admin console, a NestJS GraphQL API, and a local infrastructure stack. These pages document each system as it is actually implemented - one page per system, each with a diagram, the algorithm, a verified call trace through real files and functions, the edge cases, and the specs that cover it.

The shape of the system

Request path

A browser request reaches Next.js. Server components fetch their initial data through a per-request Apollo client that forwards the visitor's IP and the Clerk token; client containers fetch the rest through the browser client. Both hit one GraphQL endpoint. Inside the API, a request passes the Clerk middleware, a request id, the globally registered throttler guard, then either no guard (public), an optional-auth call, AuthGuard or AdminGuard, then a resolver, a service, and Prisma.

Recurring patterns

  • Identity comes from the Clerk context, never from a GraphQL input. The User row that owns the auth id decides both identity and role.
  • Money is integer rupees end to end, with discounts floored and clamped.
  • Client-sent prices are never trusted. Customisations are re-priced from live option rows and orders are priced from FOR UPDATE-locked product rows.
  • Contended resources each have one named guard. Stock and seats use conditional updates whose affected-row count is the signal; the cart merge and workshop capacity use transaction-scoped advisory locks; every status transition uses a status-predicated compare and swap.
  • Slow or external work goes through RabbitMQ, and publishing never fails a mutation.
  • Redis is a cache and a throttler store, never a source of truth; every read degrades to the loader.
  • The frontend never hand-edits the Apollo cache. Optimism is useOptimistic over a pure, tested reducer, settled by the mutation payload or an awaited refetch.
  • Presentational components take flat props and have stories at four viewports; containers own state, fetching and effects.

Where the interesting problems are

  • Checkout - the one transaction that locks, re-quotes, decrements and redeems in a fixed order.
  • Workshops - the only capacity that cannot be a counter, and therefore the only advisory lock the correctness of a feature rests on.
  • Catalogue and search - the hybrid ranking query and the archive-as-negation invariant.
  • Storage and uploads - bytes that never pass through the API, verified by reading them back.
  • Frontend data layer - the fetch-only rule and what replaces cache editing.

How to read these pages

Every page has the same six parts. The purpose is one paragraph. The diagram is inline SVG drawn for that specific flow rather than a generic block chart. The how it works section is the algorithm or state machine, with the invariants and the races called out. Minimal theory at the bottom of that is an ordered file:function call trace, verified against the code in this worktree rather than inferred. Then the edge cases and the tests that cover them.

Every page is a single self-contained file with inline CSS and no external assets, so it opens from file://. Dark mode follows the operating system preference and can be toggled per page; the choice is remembered. The pages are also styled for print.

Where something is missing, unguarded or stale, these pages say so rather than describing the intended design. Those notes are marked as such on each page.

Storage and uploads

Images go straight from the browser to Cloudflare R2 through a presigned PUT, so bytes never pass through the API. What makes that safe is that the API afterwards reads the stored object back, decodes it with sharp, and checks it against a per-purpose spec table - deleting the object and refusing if it misses. Only keys that pass are written into a confirmed_uploads ledger, and every entity save re-asserts against that ledger before persisting an image URL.

Architecture

How it works

Configuration

readR2Config() requires all five of R2_ACCOUNT_ID, R2_ACCESS_KEY_ID, R2_SECRET_ACCESS_KEY, R2_BUCKET and R2_PUBLIC_URL; any gap leaves isEnabled false. The trailing slash is stripped from the public URL and the S3 client points at https://<accountId>.r2.cloudflarestorage.com with region auto. Module constants: seven upload folders, an allowlist of JPEG, PNG, WebP and AVIF, MAX_IMAGE_BYTES of 8 MB and a presign lifetime of 600 seconds.

Presigning

  1. createAdminUpload(purpose, content_type, size) is @AdminRequired(). It checks the content type against the allowlist and that the size is above zero and within 8 MB.
  2. folderFor(purpose) and extensionFor(contentType) build a synthetic filename <purpose>.<ext>; the client's own filename never reaches the key on this path.
  3. StorageService.createImageUpload re-checks type and size, sanitises the name to lowercase alphanumerics and dashes keeping the last 80 characters, and builds the key as <folder>/<timestamp>-<4 random bytes hex>-<safeName>. That makes collisions effectively impossible and keys unguessable enough that one presign cannot overwrite another's object.
  4. getSignedUrl over a PutObjectCommand that includes ContentType and ContentLength, so the browser cannot PUT a larger body than it declared.

Confirming

UploadsService.confirm(key, purpose) is where the real file is inspected for the first and only time.

  1. The first path segment of the key must equal folderFor(purpose), which stops a category tile being confirmed as a product photo.
  2. StorageService.readObject(key) pulls the bytes back; a missing body is That upload is no longer in the bucket.
  3. sharp(body).metadata() decides the real format and dimensions; a decode failure is That file does not read as an image.
  4. checkImage(purpose, { width, height, format, bytes }) checks, in order: the decoded format against the allowlist, the byte size, that dimensions exist, then either the shortest side (for REVIEW, whose ratio is null) or both minimum dimensions followed by the ratio within RATIO_TOLERANCE = 0.02 relative.
  5. On any problem the object is deleted and then the error is thrown, so a rejected upload does not linger in the bucket.
  6. On success it upserts a confirmedUpload row keyed on the object key, which makes re-confirmation idempotent, and returns the public URL and the measured dimensions.

The ledger

confirmed_uploads has key as its primary key plus purpose, width, height, bytes and created_at. purpose is stored as plain text rather than the enum, and the API compares it against the enum string at query time. There is no foreign key to anything and no index beyond the primary key.

Enforcement at save time

assertConfirmed(urls, alreadySaved, purpose?) is what every entity write calls before persisting image URLs. It returns immediately when storage is disabled or the list is empty; it grandfathers URLs already on the row being edited, so an old image survives a re-save after the spec table changes; it maps each remaining URL back to a key, rejecting anything outside the bucket with Images must be uploaded through the console; and it requires a confirmed row for each key, matching on purpose, else One of these images was never confirmed against the size and ratio rules. The purpose match is what stops a 600 by 600 category tile being reused as a product photo.

Callers: the admin products service (twice), the admin catalog service (four times, for categories and collections), the admin events service (twice), the admin workshops service, and the admin content service for both the content hero and the site hero. The storefront review path does not call it; see the reviews page.

The console uploader

useImageRequirement(purpose) reads the rules from the imageSpecs query with a cache-first policy, and the field renders a placeholder until they arrive, so the browser never validates against hardcoded numbers. Then: checkFile on type and bytes; measureFile via createImageBitmap, closing the bitmap; checkDimensions returning ok, too-small or wrong-ratio. too-small is fatal before any dialog opens, because cropping cannot add pixels. wrong-ratio runs cropToRatio, which draws the centreCrop rectangle onto a canvas and writes PNG for a PNG source and JPEG at quality 0.92 otherwise; if the centred crop would fall below the minimum it errors out before the dialog. The dialog shows the preview, and confirming runs cropToRatio a second time on the original file rather than reusing the preview blob. Object URLs are revoked in an effect cleanup.

RATIO_TOLERANCE = 0.02 is declared in both api/src/features/admin/uploads/image-specs.ts and frontend/src/features/admin/uploads/types.ts, and the check is written differently on each side (Math.abs(w / h - ratio) > ratio * TOLERANCE versus Math.abs(actual - spec.ratio) / spec.ratio > TOLERANCE). They are algebraically equal but textually divergent, so they have to be changed together.

Edge cases and failure handling

  • Without R2 the whole gate is a no-op. assertConfirmed returns immediately when storage is disabled, which unblocks local development but means a misconfigured production deploy would silently accept arbitrary URLs.
  • An image below the minimum cannot be rescued by cropping and is rejected before the dialog opens; a crop that would land below the minimum is also rejected up front.
  • Two confirms of the same key are idempotent through the upsert on the primary key.
  • A confirm racing an entity save is possible, because assertConfirmed reads outside any transaction; the console recovers by re-saving.
  • Time of check to time of use. The presigned URL stays valid for its full 600 second window, so the same key could be overwritten with different bytes after confirmation while the ledger row still vouches for it. The only mitigations are the unguessable key and the single-purpose presign; there is no ETag or version check.
  • There is no cleanup job. Nothing sweeps R2 for objects with no ledger row, nothing removes ledger rows whose URL was never attached, and nothing deletes objects when an entity's image list shrinks or the entity is deleted. Abandoned and replaced images leak indefinitely, and confirmed_uploads grows monotonically. Its unused created_at column is the obvious hook for such a sweeper.
  • The gallery uploader silently drops a duplicate URL rather than saying so.

Tests

  • api/src/features/admin/uploads/uploads.service.spec.ts covers checkImage (a ratio two percent off the spec is allowed, further off is rejected, review photos only check the shortest side) and the service (presigning into the folder that matches the purpose, recording a matching upload and returning its public URL, deleting and rejecting an upload that misses the spec, rejecting a key from another purpose's folder, grandfathering URLs already saved on the row being edited, and skipping the check entirely when storage is not configured).
  • frontend/src/features/admin/uploads/types.test.ts covers checkFile, checkDimensions, centreCrop and moveUrl. Stories: ImageCropDialog, ImageDropField and ImageStrip.

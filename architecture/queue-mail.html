Queue and mail

Slow or external work leaves the request path through RabbitMQ: search embeddings, transactional email, telling a waiting list a piece is back, and deleting an object from the bucket. Five jobs are declared in one file with a zod schema each, every consumer re-validates before acting, and publishing is wrapped so that a broker outage can never fail a mutation. There is exactly one delivery attempt per message; anything that throws is dead-lettered to a durable queue for manual replay.

Architecture

How it works

The registry

api/src/queue/jobs.ts is the whole contract: QUEUE_EXCHANGE = "poetry", DEAD_LETTER_EXCHANGE = "poetry.dlx", DEAD_LETTER_QUEUE = "poetry.dead-letters", a jobSchemas object mapping each routing key to a zod schema, and queueNameFor(job) which prefixes the exchange name. JobName and JobPayload<Name> are derived from that object, so a typo in a publish call does not compile.

mail.send.to is validated as a non-empty string rather than an email address, deliberately. The two newest jobs carry the smallest payload that will do: a product id and a bucket key. Neither carries an email address, a rendered body or a list of recipients, so a message sitting in the dead letter queue leaks nothing and the consumer re-derives everything from the database.

notify.back-in-stock is published by NotificationsService.announceRestock from exactly two places, the console's stock adjustment and an order cancellation or refund; the batch and its duplicate guards are on the notifications page. storage.delete-object has two publishers, both of them reclaiming a customer photo nobody kept: ReviewsService.deleteObjects, for a photo an edit dropped or a removed review left behind (see the reviews page), and PendingUploadsService.sweep, for a reference photo presigned and then abandoned (see the commissions page). Admin images have no publisher at all.

Topology

  • poetry - topic exchange, durable.
  • poetry.dlx - fanout exchange, durable, with the durable queue poetry.dead-letters bound to it on an empty routing key.
  • One durable queue per job, named poetry.<job>, bound to poetry on the job name as the routing key, each declaring deadLetterExchange: "poetry.dlx".
  • prefetchCount: 4, enableControllerDiscovery: false, connectionInitOptions: { wait: false } so boot never blocks on the broker, and registerHandlers: env.QUEUE_CONSUMERS_ENABLED && !env.isTest so a replica can be publish only.

Registering a consumer

api/src/queue/subscribe.decorator.ts:SubscribeJob(job) wraps RabbitSubscribe with the exchange, the routing key, the queue name and the dead letter option, so a consumer is one decorator and a method. Because controller discovery is off, only injectable providers are scanned. Every consumer takes an unknown payload and re-validates it with the shared schema before acting, so a publisher and consumer that have drifted fail closed into the dead letter queue rather than acting on a malformed message.

Retry policy

defaultSubscribeErrorBehavior is MessageHandlerErrorBehavior.NACK. There is no retry, no backoff, no attempt counter and no delayed retry queue. A handler that throws NACKs without requeue, so the broker dead-letters the message straight to poetry.dead-letters, where it sits durably for manual inspection or replay. A zod parse failure and a transient SMTP error are treated identically: one attempt, then the dead letter queue. Publishes are persistent, so queued jobs survive a broker restart.

Publishing

QueueService.publish(job, payload) calls amqp.publish(QUEUE_EXCHANGE, job, payload, { persistent: true }) inside a try-catch that logs queue publish failed with the job, the payload and the message, and swallows the error. Publishing can never fail a mutation. isConnected proxies the AMQP connection state for the health check.

Mail rendering

api/src/mail/templates/layout.ts:renderMail(content) is the single renderer. MailContent is a title, an intro, optional blocks of a heading and lines, and an optional call to action of a label and a path. It emits inline-styled, table-free HTML - one 560 pixel column on a warm page, a white card and a sage call to action button - and a plain text twin built from the same content. escapeHtml escapes every interpolated value, which is the only injection boundary in the mail path, and the call to action href is env.FRONTEND_URL plus the path, so templates never carry a full URL.

Sending

MailService.enqueue(message) is just queue.publish("mail.send", message). MailService.deliver builds the transporter once in the constructor from env.SMTP_HOST and env.SMTP_PORT (secure when the port is 465), with auth only when both user and password are set. Both MailModule and QueueModule are global, so no feature module imports them.

Edge cases and failure handling

  • RabbitMQ down at boot: the app still starts, because the connection does not wait. GET /health reports queue: down, which fails the whole health result so an orchestrator can act.
  • RabbitMQ down while publishing: the mutation still succeeds and returns. The job is lost. There is no outbox table, no local spool and no replay hook, so recovery means reading the queue publish failed log line, which contains the full payload - including recipient addresses and rendered HTML, which is worth knowing before shipping those logs anywhere.
  • Search indexing degrades the same way, so a product edit can silently leave a stale embedding until the next edit or a pnpm search:reindex.
  • SMTP not configured is the local development path: the transporter is null, deliver logs and returns, and the message is acked and dropped.
  • SMTP configured but failing dead-letters on the first attempt, so a thirty second outage parks every mail sent during it in poetry.dead-letters until someone replays it by hand. There is no dead letter consumer, no alert on queue depth and no metric.
  • A malformed payload behaves identically to a delivery failure: one attempt, then the dead letter queue.
  • In-flight messages survive a reconnect: unacked messages are redelivered and the library re-asserts exchanges, queues and bindings on its own.
  • Out of order processing is possible with prefetchCount: 4; for search indexing the last write simply wins.
  • A redelivered notify.back-in-stock mails nobody, because the consumer's claim and its select are one statement. That is the only job whose handler is idempotent by construction rather than by accident.
  • A dead-lettered storage.delete-object leaks one object and nothing else; whatever it belonged to — a removed review, or a reference photo nobody used — is already gone from the database, so the job is the only thing that knew about the object.

Tests

  • api/src/queue/jobs.spec.ts covers the registry: one durable queue per job under the topic exchange, the exchange and dead letter names the module binds, and a parse test per payload, storage.delete-object included: a non-empty string key parses, and a blank or non-string key does not. api/src/storage/storage.consumer.spec.ts covers the handler on the other end. api/src/queue/queue.service.spec.ts covers routing, a mail payload the consumer accepts, a swallowed broker failure, a non-Error rejection being logged, and isConnected.
  • api/src/mail/templates/templates.spec.ts runs 61 cases with snapshots, and api/src/mail/templates/orders.spec.ts covers the reference photo and gift blocks. The retry behaviour and the topology beyond the names are still untested, and backInStockMail, orderStudioNoteMail and both commission templates have no direct template test.
  • Queue and mail behaviour is observed indirectly through service specs that mock MailService, including newsletter.service.spec.ts, contact.service.spec.ts and the order, event, workshop, commission and visit service specs, which assert that the right mails are enqueued.
  • api/src/features/notifications/notifications.consumer.spec.ts is the one consumer with a spec: it covers unwrapping the payload to a bare product id, refusing anything else without mailing, letting a failure escape so the broker can dead-letter it, and listening on its own durable queue. MailConsumer, SearchConsumer and StorageConsumer have none.
  • api/test/app.e2e-spec.ts boots the whole module with the queue mocked and asserts the health endpoint and the unauthenticated error shape.

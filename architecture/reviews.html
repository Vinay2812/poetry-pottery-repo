Reviews

A review is one row per subject per customer, allowed only after a delivery or an attended event, with the subject's average and count denormalised onto the product or event row. Those counters are recomputed in full on every write rather than incremented, moderation is a single hidden flag rather than a queue, and photos take a lighter path than admin uploads: presigned straight to R2, checked in the browser, and verified on the server only as far as "this is our own bucket".

Architecture

How it works

Eligibility

ReviewsService.ineligibleReason asks the transactional tables directly.

  • Product: at least one orderItem for that product on an order belonging to the user whose status is DELIVERED. Otherwise You can review a piece once it has been delivered to you. Pending, shipped and cancelled orders do not qualify.
  • Event: at least one eventRegistration for that event and user with status CONFIRMED, on an event that is either COMPLETED or has already ended. Otherwise You can review an event after attending it.
  • Anonymous visitors get Sign in to review.

One review per subject per user is enforced by @@unique([product_id, user_id]) and @@unique([event_id, user_id]), and a lost duplicate race is caught as Prisma P2002 and re-thrown as a conflict. Eligibility is checked on create only, never on update, so someone who reviewed a delivered order that is later refunded keeps their editing rights.

subjectOf throws when a review is attached to neither a product nor an event; the schema allows both foreign keys to be null and the code asserts that exactly one is set.

The rating counters

refreshRating(subject) does not increment. It aggregates _avg and _count over the subject's non-hidden reviews and writes both onto the product or event row, rounding the average to one decimal place. There is no SELECT ... FOR UPDATE and no advisory lock here, and it runs at the default read committed isolation inside the caller's transaction. Two concurrent reviews on the same product can therefore both read the pre-insert set and write the same stale pair; because it is a full recompute rather than a delta, the next review, hide or delete corrects it.

This is the one counter in the system without a concurrency guard. Elsewhere the codebase does take them: orders.service.ts:lockCartProducts uses SELECT ... FOR UPDATE in id order, cart.service.ts takes pg_advisory_xact_lock(userId, productId), and workshops.service.ts takes pg_advisory_xact_lock(configId).

Moderation

There is no status enum and no pending queue: reviews publish on write, and moderation is the single boolean is_hidden, added by api/prisma/migrations/20260914100000_review_moderation/migration.sql together with an index on (is_hidden, created_at) that serves the admin list's ordering. The migration needs no backfill because the default is false.

is_hidden: false is filtered in the storefront list, in the groupBy that builds the rating distribution, in recent, and in the refreshRating aggregate, so hiding a review removes it from the page, the counts, the summary and the denormalised average together. Admin hiding runs the update and the recompute in one transaction; admin deletion forwards to the shared ReviewsService.remove with the admin flag, which swaps the ownership-scoped where clause for an id-only one.

The admin list filters by subject kind, rating, a tri-state is_hidden and a case-insensitive search over the body or the reviewer's email, and toAdminReview passes a null viewer so is_mine is always false in the console.

Photos

createReviewImageUpload is @AuthRequired() and @StrictThrottle() and presigns straight into the reviews folder. Server-side validation of the attached URLs happens only in ReviewsService.validate: trim, dedupe, at most MAX_IMAGES = 3, and storage.isOwnUrl(url) else Review photos must be uploaded through the site. The body is capped at MAX_BODY = 1000 and the rating is truncated into 1 to 5.

Review photos never go through UploadsService.confirm, so there is no sharp decode, no dimension check and no confirmed_uploads row. Dimension enforcement is browser side only, in frontend/src/features/reviews/types.ts:checkReviewFile (JPEG, PNG and WebP, with no AVIF unlike the API's allowlist) and checkReviewDimensions (at least 400 px on the shortest side).

Display helpers

  • displayName is the first token of the name, else the email local part, else A customer, so full identities never leave the API.
  • summariseCounts clamps ratings into the 1 to 5 buckets, rounds the average to one decimal and returns a zeroed summary for an empty set.
  • recent(limit) shows reviews rated 4 or better with a body, not hidden, whose subject is an active product or a published or completed event, capped at 12 with a resolver default of 6.

The client

frontend/src/features/reviews/types.ts holds the optimistic model: a ReviewAction of post, edit or remove, applyReviewAction with withReviewAdded, withReviewUpdated and withReviewRemoved, and applyRatingChange, which recomputes the average from the distribution. toDraftReview uses DRAFT_REVIEW_ID = -1 for the not-yet-saved row. ReviewsPanelContainer wires that through useOptimistic; ReviewActionContainer passes no optimistic callback, which is what switches toRefetchNames to a smaller refetch set. useReviewList pages with fetchMore, one of the four sanctioned updateQuery uses in the frontend.

Edge cases and failure handling

  • Concurrent reviews can leave a stale rating. The recompute is lock free, so two writers can both read the pre-insert set. It self corrects on the next write.
  • A lost duplicate race becomes ConflictException rather than a raw Prisma error.
  • Eligibility is not re-checked on update, so an order later refunded does not revoke editing.
  • A hidden review is still visible to its author as my_review, because eligibility does not filter is_hidden, and they can still edit it.
  • Review photos are not confirmed. isOwnUrl is a prefix match on the public R2 URL, so any key in the bucket, including another purpose's folder or another user's review photo, is accepted.
  • There is no cleanup job. No cron, interval or queue job sweeps abandoned uploads. Deleting a review removes the row but not its objects, and replacing image_urls during an edit orphans the old ones.
  • Deleting a product cascades its reviews without calling refreshRating, which is moot for the deleted product and touches no other counter.
  • deleteReview is authenticated but not strict-throttled, unlike create, update and the photo presign.

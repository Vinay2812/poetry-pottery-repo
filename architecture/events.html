Events and registrations

An event holds a mutable available_seats counter beside its total_seats, and every seat movement goes through a conditional update rather than a lock: taking seats decrements only where enough remain, and a zero affected-row count is how the loser of a race finds out. Registrations then move through a small transition table shared by the guest and the admin console, guarded by a status-predicated compare and swap so a seat can never be released twice.

Architecture

How it works

The surface

  • Public: events(filter), event(slug) and upcomingEvents(limit) (clamped to 1 to 12). event(slug) excludes only DRAFT, so a cancelled event is still reachable by its URL.
  • Optional auth: the my_registration field resolver short-circuits when the parent already carries it, otherwise calls tryAuthenticate and returns null for anonymous visitors.
  • Authenticated: registerForEvent (also @StrictThrottle()), myRegistrations, registration(id) and cancelRegistration(id, reason), all scoped by user.db_user_id.
  • Admin: list and detail, create, update, publish, unpublish, complete, cancel with a reason, the registrations list and setRegistrationStatus.

Registering

EventsService.register validates before it holds anything: seats are truncated and must be between 1 and MAX_SEATS_PER_REGISTRATION = 4; the note is trimmed to 500 characters; a missing or draft event is a 404; an event that is not published or whose starts_at has passed raises Registrations for this event have closed; an existing pending or approved row raises You already have a seat request and a confirmed one raises You are already confirmed.

Then, inside the transaction, the seat guard:

  • event.updateMany({ where: { id, available_seats: { gte: seats } }, data: { available_seats: { decrement: seats } } }).
  • held.count === 0 is the loser's signal. There is no row lock and no advisory lock: Postgres serialises the concurrent updaters on the row and re-evaluates the predicate after the wait.
  • The error text is read from the pre-transaction snapshot, so the number in Only N seats left can be optimistic under contention. Correctness is unaffected.

Because of @@unique([event_id, user_id]), a guest who previously cancelled or was rejected gets their existing row updated rather than a new one created, with every status timestamp and the cancel reason reset to null.

  • SEAT_HOLDING = [PENDING, APPROVED, CONFIRMED]: seats are held in these states.
  • CUSTOMER_CANCELLABLE = [PENDING, APPROVED]: a guest can back out only before confirmation. Registration.can_cancel additionally requires that the event has not started.
  • releasesSeats(from, to) is true when the old status held seats and the new one does not; takesSeats is the mirror and can never fire given the terminal states, but applyStatus still handles it defensively with a conditional decrement.
  • STATUS_TIMESTAMP maps APPROVED, CONFIRMED, REJECTED and CANCELLED to their *_at columns; PENDING has none.

applyStatus

  1. canTransition guard, else a bad request naming both statuses.
  2. Compare and swap: eventRegistration.updateMany({ where: { id, status: current.status }, data: { status: next, [stamp]: now, cancel_reason when closing } }). A zero count raises ConflictException("This registration was just updated, refresh and try again"). This is what stops a double seat release.
  3. If the transition releases seats, an unconditional increment on the event, which is safe precisely because step 2 won.
  4. If it takes seats, a conditional decrement whose zero count raises Not enough seats left to reopen this registration.
  5. A fresh read with the event included.

Cancelling and admin cancellation

A guest cancel finds the row scoped by user, checks can_cancel, and calls applyStatus with the trimmed reason or Cancelled by the guest, then notifies after the transaction. An admin cancelling a whole event trims the reason (defaulting to The studio called this one off), loads every pending, approved and confirmed registration, and walks them in a serial loop of applyStatus plus notifyStatus, before finally setting the event status, which also requests a search reindex.

Listing

eventWhenWhere(when, now) is deliberately complementary. Past is published or completed and either completed or already ended; upcoming is published and ends_at >= now. An evening that is running right now therefore stays on the upcoming tab, and cancelled or draft events appear on neither. Search runs through search.rankEvents(term, 100), an empty ranked set short-circuits, and ordering is starts_at descending for past and ascending for upcoming.

Seat capacity edits

AdminEventsService.update asserts the schedule (end after start, integer price at or above zero, at least one seat), checks the images through assertConfirmed, and then applies the seat delta as available_seats: Math.max(0, current.available_seats + seatDelta), so shrinking the room never drives the counter negative. create sets available_seats = total_seats.

Mails

notifyPlaced sends the guest a confirmation and, when env.BUSINESS_EMAIL is set, the studio a copy. registrationStatusMail returns null for PENDING, so no mail is sent for it, and has copy for approved ("Your seat is held"), confirmed, rejected (including the reason when set) and cancelled. Every enqueue happens after the transaction commits.

The client

  • useEvents falls back to previousData so filter changes do not flash skeletons, and paginates with fetchMore plus updateQuery, which is the sanctioned pagination carve-out from the fetch-only rule.
  • useRegisterForEvent wraps the mutation in requireAuth, then calls router.refresh() because the event page is a server component holding a now-stale seat count, and pushes to the registration page with ?placed=1.
  • EventDetailContainer clamps the seat stepper to Math.max(1, Math.min(MAX_SEATS, event.available_seats)), mirroring the server's limit of four, and hides a cancelled or rejected my_registration so the guest can book again.
  • RegistrationDetailContainer uses useOptimistic(registration, applyRegistrationCancellation); the review call to action appears only for a confirmed registration on a past event.
  • EventListContainer parses filters from the URL, holds them in useOptimistic and navigates with router.replace; changing the event type clears the level.

Edge cases and failure handling

  • Two guests taking the last seat: the conditional decrement means exactly one wins.
  • A double cancel cannot credit seats twice, because the compare and swap means only one transition wins and the loser gets a conflict.
  • A previously cancelled guest re-registering reuses their row rather than violating @@unique([event_id, user_id]).
  • Shrinking a room clamps available_seats at zero rather than going negative. There is no database level check constraint on the column; non-negativity lives entirely in the predicate and that clamp.
  • Cancelling an event is not atomic across registrations. It is a serial loop with no surrounding transaction, so a failure part way through leaves some guests cancelled and the event still published.
  • The "only N seats left" number can be stale under contention, because it is read from the pre-transaction snapshot.
  • Mails are enqueued after commit and their failure is not swallowed, so a mail-enqueue error rejects the mutation even though the registration is committed.

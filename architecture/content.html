Content, settings, newsletter and contact

The marketing surface - editable pages, the site settings singleton, the announcement bar, the newsletter and the contact form - shares one shape: a short-lived Redis cache in front of a database read, dropped explicitly on an admin write, with every cache read degrading to the loader when Redis is unavailable. The two public write paths, subscribing and contacting, are both strict-throttled, both persist before they send anything, and both hand the actual sending to the queue.

Architecture

How it works

The cache primitive

RedisService.getOrSet(key, ttlSeconds, loader) catches the read, parses with reviveDates (an ISO string pattern turned back into a Date, because JSON drops them and the GraphQL DateTime scalar needs them back), and on a miss calls the loader and writes with an expiry, catching that too. No cache is ever authoritative: a Redis outage degrades to uncached reads, never to an error. The client is built with lazyConnect, maxRetriesPerRequest: 2 and enableOfflineQueue: false, and a failed connect at boot is logged rather than fatal.

Every Redis cache in the API. All go through RedisService.getOrSet, which degrades to the loader on any Redis failure. Redis also holds the throttler counters and the per-customer review upload set, neither of which is a cache.

Invalidation is delete-after-write with no versioning, so a concurrent getOrSet that already read the old row can write it back just after the delete and serve stale data for up to the TTL. The short TTLs bound it; nothing else prevents it. Two of the five keys have no invalidation at all and lean entirely on their TTL.

Content pages

contentPage(slug) is public, unguarded and unthrottled, and reads through the cache. The loader is a findFirst on slug plus is_published, so an unpublished or missing page caches its null for 120 seconds and raises NotFoundException("Page not found") on each hit.

The admin side has six operations, all @AdminRequired(). saveContentPage slugifies (an empty result raises A page needs a slug), grandfathers the currently saved hero image through assertConfirmed at UploadPurpose.CONTENT, and then delegates to ContentService.update, which owns the zod schema and the cache key. The schema allows a title of 2 to 160 characters, an optional subtitle up to 240, a hero image that is a URL or blank, at most 20 sections each with a heading and a body up to 5000 characters, and at most 20 items per section. Only the first zod issue is surfaced.

deletePage(slug) deletes with the raw slug and invalidates contentCacheKey(slug), while savePage writes under slugify(slug). A non-normalised slug can therefore miss on delete where save would have normalised it.

Site settings and the announcement bar

SettingsService.get() reads the singleton row with findUniqueOrThrow({ where: { id: 1 } }) behind the settings:site key; the row is inserted by the initial migration, so a missing one is a genuine fault. updateSettings validates the money fields as non-negative integers, checks a changed hero image at UploadPurpose.HERO, and then writes field by field so only the keys that were sent are touched. Two fields, free_shipping_above and hero_image_url, treat an explicit null as a meaningful clear rather than a skip.

updateAnnouncement trims the text to 160 characters; a blank text takes the bar down and forces the href to null, while a present text keeps an href trimmed to 300. The storefront layout renders AnnouncementBar only when settings.announcement_text is set.

Newsletter

subscribeToNewsletter is public and @StrictThrottle(), and uses tryAuthenticate so a signed-in visitor's subscription is linked to their account. Inside a transaction it reads any existing row, computes linkableUserId and upserts on the email. linkableUserId guards the unique user_id column: it returns the user id only when no other subscriber row owns it, so a second address for the same account subscribes unlinked instead of failing on a duplicate key. Re-subscribing an already active address is idempotent and sends no second welcome, because wasActive is snapshotted before the upsert and the mail is enqueued after the transaction commits.

The unsubscribe token is a Prisma column default: token String @unique @default(nanoid(24)), generated in the database on insert. It is not signed and does not expire; it is a bearer capability that only ever appears in the mail call to action, built as /newsletter/unsubscribe?token=... against env.FRONTEND_URL. Verification is a plain updateMany({ where: { token }, data: { is_active: false, unsubscribed_at: now } }), whose zero count is a NotFoundException. Using updateMany rather than update means an unknown token is a miss rather than a Prisma throw, and unsubscribing twice still succeeds because the row matches on token regardless of its active flag. The strict throttle is the only defence against guessing the token space.

The admin unsubscribe matches on the lowercased email and is_active: true, so a second call raises That address is not on the list, unlike the token path.

Contact

sendContactMessage is public and @StrictThrottle(). The zod input allows a name of 2 to 80, a lowercased email, an optional phone run through the shared normalisePhone, an optional subject up to 120 and a message of 10 to 2000 characters. The row is created first, so the studio never loses a message to a mail failure. Then the studio mail goes out when env.BUSINESS_EMAIL is set, and an acknowledgement always goes to the sender. The function returns true unconditionally.

The acknowledgement goes to an unverified, caller-supplied address with only the strict throttle in front of it, which is a reflection vector bounded at five per minute per tracker.

Admin inbox

adminContactMessages filters on a tri-state read flag and a contains search across name, email, subject and message. setContactMessageRead and deleteContactMessage are raw updates and deletes, so a missing id surfaces as a Prisma error rather than a NotFoundException.

The module carries two exports, both queries that perform an export, returning a whole RFC 4180 quoted CSV as one GraphQL string, capped at EXPORT_LIMIT = 10000 with no streaming and a silent cap. toCsv writes email,status,subscribed_at,unsubscribed_at for subscribers; toWatcherCsv writes email,piece,requested_at,notified_at for the back-in-stock waiting list, which also lives in this module. The browser turns the string into a file itself. The waiting list is described on the notifications page.

The inbox module does not handle commission briefs, despite the console route being called the commission inbox; those three admin fields sit on CommissionsResolver. See the commissions page.

Edge cases and failure handling

  • Redis down is invisible to callers: every cache read falls through to the loader.
  • Stale reads for up to the TTL are possible after an admin write, because invalidation is unversioned.
  • A null page is cached too, so publishing a page can take up to 120 seconds to appear.
  • deletePage does not slugify, so a non-normalised slug can miss.
  • A second address for one account subscribes unlinked rather than violating the unique user_id.
  • Re-subscribing sends no second welcome, because the active flag is snapshotted before the upsert.
  • The unsubscribe token never expires and is not signed. It must never be logged; the strict throttle is the only brute-force defence.
  • A contact message is stored before any mail is attempted, so a mail failure never loses it.
  • Both exports are capped silently at 10000 rows and returned as one string.
  • The commission options cache never invalidates. An admin adding a size or a glaze waits up to 120 seconds for the brief form to offer it, and the helper that would have fixed that is dead code.

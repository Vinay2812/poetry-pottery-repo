Back in stock notifications

Pottery is made in kiln loads, so a sold-out piece is not gone, it is between batches. A shopper leaves an address against the piece, and when stock crosses back above zero the API publishes one job that mails everyone still waiting. Three separate guards keep that from turning into duplicate mail: an edge test that only fires on the crossing itself, a status-predicated order transition that lets one cancellation win, and a claim-before-send that stamps every waiting row inside the same statement that selects it.

Architecture

How it works

The waiting list

BatchNotification, @@map("batch_notifications"), carries an email, a product_id, an optional user_id (onDelete: SetNull), a token String @unique @default(nanoid(24)), a nullable notified_at and created_at. The schema comment is the whole product decision: someone waiting for a sold-out piece to come out of the next kiln load.

  • There is no status enum. notified_at IS NULL means still waiting; a stamp means already mailed.
  • @@unique([email, product_id]) is what makes a burst of taps one row.
  • @@index([product_id, notified_at]) is exactly the shape the batch claim queries on.
  • The token is a bearer capability generated by a Prisma column default, unsigned and non-expiring, the same pattern as the newsletter unsubscribe token on the content page.

Joining the list

notifyWhenBackInStock(product_id, email) carries no auth guard and @StrictThrottle(), and calls authGuard.tryAuthenticate so a signed-in watch is tied to the session rather than to whatever address was typed. NotificationsService.watch:

  1. Normalises the address through parseEmail, the same trim-lowercase-validate pipe the newsletter uses.
  2. Refuses an unknown or inactive piece with That piece is no longer listed, and a made-to-order one with That piece is made to order. A piece thrown to order has no next batch to wait for, so there is nothing the mail could ever announce.
  3. Reads the existing row to compute was_already_waiting, which is true only when a row exists and its notified_at is still null.
  4. upsert on email_product_id, whose update branch sets notified_at: null and attaches the user id when there is one. An already-mailed row is deliberately put back in the queue for the next batch, so someone who missed a load can wait for the following one.

On the client, the form appears exactly where the service would accept it: canWatchPiece(stock, isCustomizable, isActive) is isActive && !isCustomizable && stock <= 0. It used to short-circuit on is_archived and offer itself on any archived piece whatever its stock. But is_archived is true for a piece the studio has taken down and for a made-to-order piece whose collection window has closed, and those are the two cases the API refuses outright, so the form asked for an address only to answer with an error. The three flags it reads now are the same three the service checks.

The two places stock crosses upward

api/src/features/notifications/restock.ts is four lines and does the entire decision:

cameBackInStock(before, after) returns before <= 0 && after > 0. A top-up of a shelf that already had pieces on it is not a restock, so 2 → 5 is silent while 0 → 3 fires. The <= 0 rather than === 0 covers a shelf that was somehow negative.

Made-to-order lines never restock and are skipped in the second case, because their stock never moved.

The job

announceRestock(productId) is a one-line queue.publish("notify.back-in-stock", { productId }). The payload schema in api/src/queue/jobs.ts is a single integer, and the routing key gives the durable queue poetry.notify.back-in-stock bound to the poetry topic exchange with poetry.dlx attached, exactly like the other four jobs on the queue page. QueueService.publish swallows broker failures, so a restock never fails an admin edit or an order cancellation; it just loses the announcement.

NotificationsConsumer.backInStock re-parses the payload with the shared schema before acting and lets anything else throw, so a malformed message dead-letters rather than being guessed at.

Claim, then send

NotificationsService.sendBackInStock(productId) is where duplicate mail is actually prevented.

  1. Read the piece. !product?.is_active || product.stock <= 0 returns 0 immediately, so a job that arrives after the batch sold out again mails nobody.
  2. Claim in one statement: batchNotification.updateManyAndReturn({ where: { product_id, notified_at: null }, data: { notified_at: new Date() }, select: { email, token } }). The rows are stamped by the same statement that returns them, so a redelivery, a double publish or two consumers finds nothing left to claim.
  3. Enqueue one mail.send per claimed row and return the count.

backInStockMail(productName, productSlug, token) gives each recipient their own stop link, /notify/unsubscribe?token=..., and a call to action back to the piece.

Leaving the list

stopBatchNotification(token) is also unguarded and strict-throttled. It is a deleteMany on the token, and a zero count is NotFoundException("That link has already been used") — a delete rather than a flag, so the address is gone rather than suppressed.

There is no /notify page. The directory holds only unsubscribe/page.tsx; the sign-up form lives on the product page. The unsubscribe route fires its mutation from an effect guarded by a useRef, because React StrictMode's double invoke would otherwise spend the single-use link twice and show the visitor the "already used" error for their own first click. A 404 from the server is mapped to That link has already been used or has expired.

The waiting list in the console

adminBatchNotifications(filter) and exportBatchNotifications(filter) live on AdminInboxResolver beside contact messages and newsletter subscribers, both @AdminRequired(). The filter's is_notified maps to notified_at: { not: null } or notified_at: null, and search matches the address and the piece name together.

The export is a query that performs an export, the same shape as the subscriber CSV: toWatcherCsv(rows) returns one RFC 4180 quoted string with the header email,piece,requested_at,notified_at, and the browser turns it into a file locally, building a Blob, clicking a synthetic <a download> and revoking the object URL. The filename is dated in studio time by toWatchersCsvName. The console route is /dashboard/notifications, labelled Waiting list in the rail.

Edge cases and failure handling

  • A redelivered job mails nobody. The claim and the select are one statement, so the second delivery finds no rows with notified_at: null.
  • A top-up is not a restock. The edge test is the reason the console can correct a stock count of three to five without waking the whole waiting list.
  • Two concurrent cancels announce once, because the status-predicated transition means only one of them releases stock at all.
  • Announcing after commit is deliberate. A publish inside the transaction would announce a restock that a rollback then undid.
  • A broker outage loses the announcement silently, since publish swallows its error. The waiting rows keep their null stamp, so the next restock of the same piece mails them.
  • The piece can sell out again before the consumer runs, which is why sendBackInStock re-reads the stock and returns zero rather than mailing about an empty shelf.
  • Re-watching clears an old stamp, so somebody who missed one load is queued for the next.
  • The token is unsigned and never expires, and appears only in the mail; the strict throttle is the only defence against guessing.
  • StrictMode would spend the stop link twice without the ref guard on the unsubscribe effect.
  • Nothing prunes the table. Mailed rows stay with their stamp until the piece is deleted, which cascades them.

Tests

  • api/src/features/notifications/restock.spec.ts pins the edge in both directions: 0 → 3 and -1 → 1 fire, 2 → 5, 1 → 1, 0 → 0 and 3 → 0 do not.
  • api/src/features/notifications/notifications.service.spec.ts covers lowercasing and one row per piece, was_already_waiting, an already-mailed row going back in the queue, refusing an unlisted piece and a bad address, the claim-before-mail order, staying quiet for a sold-out or delisted piece, one publish per restocked piece, and the stop link being spent once.
  • api/src/features/notifications/notifications.consumer.spec.ts covers unwrapping the payload to a bare id, refusing anything else without mailing, letting a failure escape so the broker can dead-letter it, and listening on its own durable queue.
  • api/src/features/notifications/notifications.resolver.spec.ts covers the anonymous watch, a signed-in watch being tied to the session rather than the typed address, stopping on the token alone, and both mutations carrying no auth guard.
  • api/src/features/admin/products/products.service.spec.ts asserts that a top-up announces only when the shelf was empty, and not twice.
  • api/src/features/admin/inbox/inbox.service.spec.ts covers toWatcherCsv, the header on an empty list, the notified and waiting where-clauses, and searching an address and a piece name together.
  • api/test/integration/notifications.integration-spec.ts runs eight cases against a real Postgres with fifteen racers: one row survives a burst of signups; a second delivery of the job returns zero and the address receives exactly one mail; nothing is sent while the piece is still sold out; a cancelled order that refills an empty shelf publishes the job; a cancellation that tops up a stocked shelf publishes nothing; a piece the studio has taken down is refused; a piece thrown to order is refused; and the stop link is spent once.
  • frontend/src/features/notify/types.test.ts covers canWatchPiece and the result reducer; frontend/src/features/admin/notifications/types.test.ts covers the row mapper, the notified filter, the export filter and the dated CSV name.
  • Gap: backInStockMail has no direct template test. It is covered only through the service and integration specs asserting that one mail went to the right address.

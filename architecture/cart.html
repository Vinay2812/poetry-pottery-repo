Cart

The cart is one row per user, product and selection key. Its only concurrency guard is a transaction-scoped advisory lock around the merge, because merging a quantity means reading a line and then writing it back. Availability is recomputed on every read rather than stored, so a piece that sells out or whose collection closes stays in the cart with a reason attached instead of vanishing, and every mutation answers with the whole recomputed cart so the browser never has to patch one itself.

Architecture

How it works

The surface

CartResolver exposes cart, cartCount, addToCart, updateCartItem, removeCartItem and clearCart, all @AuthRequired(), with the user id taken from @CurrentUser() and never from an input. Every mutation ends with return this.get(userId), so the reply is always the whole recomputed cart. cartCount is the exception and exists precisely so that the badge in the header does not pull a cart on every page; it counts without building one. See the shell page.

Reading a cart

CartService.get runs the line query and settings.get() in parallel, maps rows through toCartItem (unit price is the product price plus the summed selection modifiers), and then applies availability.

subtotal sums only the available lines. shippingFor(subtotal, flat_fee, free_above) returns zero for an empty cart or a subtotal at or above the free shipping threshold, and the flat fee otherwise. Because settings.get() is cached in Redis for 60 seconds, the shipping fee can lag an admin change by up to a minute.

item_count sums all lines including unavailable ones, while subtotal and total count only the available ones. CheckoutQuote.item_count on the orders side counts available lines only, so the two numbers can differ on a cart that has gone stale.

Adding, and the advisory lock

Adding is a read of the existing line followed by a write of the merged quantity, which is not atomic. Two tabs adding at once must therefore queue up, and they do, on a transaction-scoped Postgres advisory lock taken as the first statement inside the transaction:

  • SELECT pg_advisory_xact_lock(userId::int, product.id::int) - the two-integer form, keyed on the user and the piece. It releases automatically at commit or rollback.
  • The key is not the selection key, so concurrent adds of the same product with different customisations also serialise. That is coarser than needed and never deadlocks with itself.
  • The single-argument form used by workshops (pg_advisory_xact_lock(configId)) cannot collide with it, because Postgres keeps one-key and two-key advisory locks in separate spaces.

The product row is not locked here, so the stock read before the lock can be stale by the time the line is written. That is accepted: the authoritative oversell guard is the conditional decrement at order placement, described on the checkout page.

Updating, removing and clearing

  • updateQuantity scopes the lookup by user_id, which is the ownership check. A quantity of zero or less deletes the line rather than erroring, because that is what a stepper dialled to zero means. Anything above ten is refused, and assertStock runs for non-customisable pieces. There is no transaction and no lock here: a lost update between two tabs is harmless because the value is absolute and stock is re-checked at checkout.
  • remove is deleteMany scoped by id and user, so it is idempotent and an already-gone line is not a 404.
  • clear deletes every line for the user.

The optimistic provider

The optimistic layer lives in features/cart/hooks.ts:useCart(), which the cart page mounts, not in CartProvider. It reads the cart with fetchPolicy: "cache-and-network" then nextFetchPolicy: "cache-first", falls back to previousData so a refetch never flashes a skeleton, and wraps the result in useOptimistic(cart, applyCartAction) with useTransition. Because the cart is a computed object with no id of its own, the baseline after a mutation is the awaited refetch rather than the mutation payload: CART_REFETCH = { refetchQueries: ["Cart", "CartCount"], awaitRefetchQueries: true }, which is what keeps the header badge in step with the page.

CartProvider itself holds only { count, isSignedIn, isAdding, addToCart }, because those are the parts every route needs. addToCart is deliberately not optimistic. Stock is the server's call, so the button waits and exposes the mutation's loading as isAdding, then toasts success with a "View cart" action.

applyCartAction in frontend/src/features/cart/types.ts mirrors the server maths: clear empties the lines, remove filters by id, and a quantity change recomputes line_total and drops lines whose quantity fell to zero. It then recomputes subtotal over available lines, item_count over all lines, and shipping. The guard canPredictShipping(current, next, freeShippingAbove) returns false when the cart currently ships free and the next subtotal is neither zero nor still above the threshold, because a free shipping cart never reports the flat fee and so it cannot be guessed. In that case the reducer returns the cart unchanged and lets the server answer, rather than flashing a wrong total.

CartContainer renders every line, unavailable ones included with their reason, but totals and canCheckout use only the available ones. canAdjustQuantity stays true for a line that is over stock so the shopper can dial it down. "Save for later" is a wishlist toggle followed by a remove, which is two independent optimistic updates in two providers.

Edge cases and failure handling

  • A line that goes stale stays in the cart. Nothing is auto-deleted: the row comes back with is_available: false and a reason, is excluded from the subtotal, and blocks checkout through quote.problems.
  • Made-to-order lines never fail on stock, only on the active flag and the collection window.
  • Merging saturates at ten rather than raising an error.
  • The stock read in add can be stale, deliberately; the conditional decrement at placement is the real guard.
  • remove on an already-removed line is a no-op, not a 404.
  • Shipping can lag by up to 60 seconds after an admin changes the flat fee or the free shipping threshold, because of the settings cache.
  • Signed-out visitors never fire a cart query: skip: !isSignedIn plus an empty-state render, on both the badge count and the full cart.
  • The badge and the page are two documents, kept in step only because every mutation refetches both and awaits them.

Tests

  • api/src/features/cart/cart.service.spec.ts covers shippingFor, toCartItem pricing, sold out, short stock and both collection window cases, the merge and cap, the quantity range, dropping to zero, and totals with free shipping.
  • api/src/features/cart/selections.spec.ts covers the selection resolution and key.
  • api/test/integration/cart.integration-spec.ts runs two races with 20 concurrent callers against a real Postgres: 20 simultaneous adds merge into one line capped at ten, and a merged line is stopped from climbing past a stock of three, leaving exactly three wins and one row. The unit spec additionally asserts that the advisory lock was taken, by checking $executeRaw was called on the merge path.
  • frontend/src/features/cart/types.test.ts covers the reducer, including that it leaves the cart it was given alone and that it waits for the server when the shipping fee cannot be worked out.
  • The provider and container have no tests; the presentational components have stories.
